# Review — 2026-11-06

## Summary

This is the first review, so every case is new: 15 cases, 6 `fixed` and 9 `blocked`, none `unreproduced`, none
`declined`. All 15 were backfilled by pass 403 — the history file did not exist before it, so the counts below
describe closures that were already recorded in the ledger and the iteration reports, not fresh work.

The dominant fact is **9 of 15 blocked, and every one of the nine is blocked on the harness rather than on the
product**: two on upstream issues, three on the headless harness not driving hover or a real press, and four on
a pass running out of budget after locating the cause. That split is the material finding, and it is not
something a per-capture pass could see.

## Patterns

### P1 — The headless harness cannot reproduce pointer-driven defects (3 cases)

- **Hypothesis:** Three blocked cases share one cause: `harness::build_headless` does not drive
  `Hovered`/picking the way the live window does, so a defect whose symptom is "the thing under the cursor is
  not the thing highlighted" cannot be turned into a failing test at all — regardless of whether the product is
  wrong.
- **Evidence:**
  - `feedback-1793927950267` (blocked) — the row's own claim was measured wrong: the injected pointer *does*
    take logical coordinates (`sense_pointer` needs a `PrimaryWindow` to convert, so headless it returns
    `None`). The re-reproduction is owed, not done.
  - `feedback-1793928159971` (blocked) — the hover band centres 77 physical px (38.5 logical) below the
    recorded pointer, reproduced *from the record*, but "seen, not testable": two whole-application attempts
    failed for harness reasons, and `Hovered` is not driven in the harness the way it is live.
  - `feedback-1793969010186` (blocked) — `bevy_gooey::testing::click` on the sidebar's Settings leaves the
    dialog closed while `write_message(OpenSettings)` opens it, so the handler is fine and the *press* does not
    arrive. Ruled out: layout, plain ancestors, `Pickable::IGNORE` on the `Text` child, and `find_by_label`
    returning the `Text` rather than its `Button` ancestor.
- **Structural fix:** make the harness able to answer "what is under this point" the way the window does. The
  pieces already exist: `WindowlessFocus` and `windowless_click_to_focus` in `bevy_gooey::testing` were added
  for the first case, and `view::sense_pointer` already computes the answer given a surface. One helper that
  takes a point in logical px and returns the `Hittest`/`Hovered` set, plus a headless window resource it can
  convert against, would turn three "untestable" rows into ordinary failing tests.
- **Guard:** a property test — for every widget with a `ComputedNode` on a screen fixture, injecting a pointer
  at that node's centre makes that node the pick, and no other node's `Hovered` is set.
- **Size:** medium. The conversion and the focus shim exist; what is missing is a window in the harness and one
  entry point that both the harness and the live path use.

### P2 — A label spawned into a band that has its own semantics reads as a member of it (2 cases, 1 blocked + 1 fixed)

- **Hypothesis:** Both cases are a widget spawned into a container whose layout *implies* a role the widget does
  not have, so it reads as a member of that run. Neither is a sizing bug; both are spawn-site bugs.
- **Evidence:**
  - `feedback-1793927698061` (fixed, `c91b218`) — Fill was spawned in the icon-only command loop although it
    carries a word, so a 107 px button sat among 65–66 px pictures. Fix: spawn it with the worded tools, before
    the separator. Cause `layout-rule`.
  - `feedback-1793928006124` (blocked) — `chrome.rs:3864-3867` spawns the `WhereYouAre` label (`ControlId::Title`)
    into the *door strip band*, where `here` is `door.label()`, so the Kit door draws a bare `Map` at x=376
    between the menu bar and the door's own tabs, reading as a fourth tab. Cause located, no failing test
    written before the budget ran out.
- **Why they are one pattern and not two:** both fixes are "move the spawn to the parent that owns that role",
  and both would be caught by the same property.
- **Structural fix:** the band's own layout should refuse an outsider. Either spawn the title band as its own
  row with `UiRect` separation from the tabs, or have the strip's spawn helper take a typed `BandMember` so a
  bare label cannot land among `Tab`s.
- **Guard:** for every band that carries `Tab`s, assert that no non-`Tab` sibling lies within the tabs' x-run —
  a containment/separation property over the strip, which is the oracle `feedback-1793928006124`'s next pass
  was told to write.
- **Size:** small for the test, medium for the typed band.

### P3 — Four `launcher.rs` fixes, four different causes: a hotspot in the file, not in a mechanism

- **Hypothesis:** `launcher.rs` carries 4 of the 6 fixes, but inspection of the four diffs says they are **not**
  one mechanism: a fill order, a padded-box width, a prose measure, and a missing `ScrollArea`. The file is hot
  because the launcher is where all four screens' chrome lives, not because it has a class of bug.
- **Evidence:**
  - `d01f0e4` — first-frame fill-order (`init-order`): the page body was laid out before the sidebar existed.
  - `9d6bdd9` — a width taken from `SIDEBAR_PX` (outer) while drawing into the padded content box, overshooting
    by `2*PAD` (`layout-rule`).
  - `f11f8f0` — prose set at the window's width, 118 characters a line (`text-measure`).
  - `b28ff38` — ten entries drawn three, with no `ScrollArea` above or inside the page (`clip-scroll`).
- **Verdict:** **not a pattern; a lead.** Reported as a hotspot because 4 ≥ 2, but the fixes changed four
  different kinds of thing for four different reasons, which is exactly the test R3 applies. No structural fix
  proposed.
- **Size:** n/a.

## Suggested corrections

- **`feedback-1793927698061`'s oracle** is recorded as `other:size-class-invariance`. It is a real oracle and a
  useful one — a button's width says which class it belongs to — but the taxonomy's five slugs do not include
  it. Suggest promoting it to a first-class oracle named `size-class`, described as "every widget's measured
  size falls inside its own class's run". One case today; the guard in P2 would produce more.
- **`feedback-1793928048623`'s cause** is recorded as `layout-rule`, but the panel has three distinct geometry
  failures (text past the right edge, two rows drawn on top of each other, a hint running off), which is at
  least as much `clip-scroll` as `layout-rule`. Left as `layout-rule` because no fix exists to read a cause off;
  a person may want to split it.
- **`feedback-1793927950267` and `feedback-1793928048623` both carry "SUPERSEDED IN PART by pass 392"** in
  their reasons: the row's original claim was a coordinate-space error, not a product fault. Their symptoms are
  recorded as they were reported (`unresponsive`, `layout`), which is right for the taxonomy — but a reader
  counting this row as evidence of a picking defect would be misled. No edit proposed to the case lines; the
  correction is recorded here instead.
