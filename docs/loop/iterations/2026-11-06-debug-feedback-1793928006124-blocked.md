# feedback-1793928006124 — the door label reads as a fourth tab

**Classification:** `bug`. *"The "Map / Kit" toggles get confused with the Meshes, Tiles, Compose tabs"* says the
screen **is** confusing; the fix it implies is not the kind.

**Outcome:** `blocked`. Reproduced on its own platform with coordinates, and **the cause is located in this
repo** — but the pass reached its budget before a test failed, so no fix is claimed and nothing shipped.

## Reproduced — measured on mac_air, metal, 2560x1604, ui_scale 2.4

On the Kit door, every laid-out `Text` in the strip row (`y = 33`), by x:

```
File 58   Edit 167   View 275   |   Map 376   |   Meshes 492   Tiles 625   Compose 765   |   Tools 1014   Help 1130
```

`Map` is drawn **in the tab strip's own row**, 116 px left of `Meshes`, between the menu bar and the door's
tabs, at the same height and baseline. `Door::tabs()` for the Kit door is `[Meshes, Tiles, Compose]` and its
own doc says *"the Kit door never offers the Map"* — so `Map` is not a tab, but nothing on screen says so.

## The cause, located

`crates/bevy_cauldron/src/chrome.rs:3864-3867`:

```rust
WhereYouAre,
// Where you are is what `N` renames, so its badge goes on the words it changes.
Control(keys::ControlId::Title),
Text::new(here),          // `here` = door.label(), chrome.rs:3899
TextColor(DIM),
```

The "where you are" label is spawned **into the door strip band**, immediately before the strip
(`tiles.rs:4152` adds the strip as a child of `frame.door_strip` too). It is a bare `DIM` label with no
separator, so on the Kit door it puts the word `Map` flush against `Meshes` and reads as the first tab.

## Why it is not fixed here

The pass reached 45 minutes with the cause located but **no failing test**, and the budget rule is explicit:
do not push an unproven fix. The reason a test was not quick is worth recording: the headless rebuild
(`capture_feedback_1793928006124::crossing_a_door_leaves_one_strip_with_that_doors_tabs`) **passes on the
base commit** — the strip's `Tab` entities and the strip count are both correct. So the failing test must
assert on the **`WhereYouAre` label's placement in the band**, not on `Door::tabs`. That is the next pass's
first move:

1. find the `WhereYouAre` entity and the first `Tab` entity in the laid-out UI;
2. assert the label is not adjacent to the tabs at the same baseline without separation — containment or a
   minimum gap, which is the oracle for "these read as one row of tabs";
3. then separate them: move the label into the chrome bar (where `MAP · bedroom` already is, `chrome.rs:3899`)
   or give the band a divider, which is a product decision the test makes safe either way.
