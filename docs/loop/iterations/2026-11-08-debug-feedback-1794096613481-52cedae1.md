## The cause, read at the pinned `bevy_gooey` `04a3cdf`

1. `centre_keycaps` (`src/prompt.rs`, `PostUpdate`) widens a keycap's `Node::padding` by `slack / 2.0`, with `slack` taken from `ComputedNode` and `TextLayoutInfo` (**physical** px) and added to a `Val::Px` (**logical**). At 2.4 physical px per logical px, a 10 px slack adds 5 logical px, not 2.1: `3.0 + 10 / 2 = 8.0`, the value read over BRP (the 10 is inferred from it). It never narrows.
2. `show_tooltips` (`src/tooltip.rs`) stores `ceil(keycap width x inverse_scale_factor)` in `TooltipBox::cap`: 19 for the 45 px cap, 25 for the 59 px one, so `TooltipBox` changes whenever the state does.
3. `apply_skin` restyles an entity whose `TooltipBox` changed, and with it its direct children (the `texts` list: "a button's text follows the button's state"), so the keycap's padding goes back to `pad * 0.5` = 3.0.

Frame by frame, from the code, which gives the sampled `A A B`: restyle, lay out A, `centre_keycaps` writes 8.0; `show_tooltips` sees A (cap 19, was 25), restyle, A, 8.0; `show_tooltips` sees A (19, unchanged), no restyle, the 8.0 lays out as B; `show_tooltips` sees B (25, was 19), restyle, and round again. This was reasoned from the code and matched against the samples, not traced frame by frame; the issue says so.

Only a tooltip with a shortcut has a keycap, which is why `Place pieces` is steady.

## Oracle

None written: the fix is in gooey. The issue's acceptance is the oracle: with a shortcut on the `Tooltip`, a window at scale factor 2 and `UiScale` 1.2 (and 1x, 1.5x), once the box is open its rect and its keycap's rect are identical on 30 consecutive frames, and the keycap's words stay centred.

A whole-application test here would need the editor's headless app to shape text. A probe of the `Erase` tooltip in `harness::build_headless` (focus-opened, 60 frames, 1280 x 703 at UI scale 1.2) kept one width after a two-frame settle (115.0 to 116.7 logical), so the loop did not run there; the probable reason is that `centre_keycaps` skips a cap whose run has no width (`text.size.x <= 0`), which I did not confirm. The probe was a scratch file in a worktree on big and was not committed.
