# 2026-11-01 reload: a game's state follows a piece a live reload draws again (#201 slice 2)

Focus: hot reload H4 (#201) · Commits: 0150191, f7db4c9 (release) · Machine: laptop (edit, review) + big (build, gate, release, accept) · Outcome: shipped

## Summary
The game-side `GrimoireLivePlugin` draws a moved, turned or retyped placement again (new entity, old one despawned), so a booking, an animation phase or a camera target on it was lost and each call site that edits a piece had to patch it. A game now registers how a kind of state moves once, on the app: `GrimoireLiveApp::carry_across_respawn::<C>()` or `migrate_on_respawn(|world, old, new| ...)`. Build step 5 of the issue (a move keeps the entity, updated in place) is blocked on an existing assertion and needs the owner.

## Enhancement: migration hooks (build step 4 of #201)
Goal: state a game hung on a piece follows it when a reload draws the piece again, through one hook per kind.
Files: `crates/bevy_grimoire/src/live.rs` (`GrimoireLiveApp`, `ReloadMigrations`, `reload`), `crates/bevy_grimoire/src/lib.rs` (`spawn_placements` returns the entities it drew, by id), `crates/bevy_grimoire/tests/live_migrate.rs`, `docs/guide/reload-contract.md`, `docs/guide/your-game.md`.
Proof: `live_migrate.rs` did not compile on the base commit (no `GrimoireLiveApp`: E0432 and E0599 in the before-run on big); 6 pass after. The 6 + 4 + 4 + 2 existing tests of the crate (`live_identity`, `live_reload`, `live_verdicts`, `paint_on_a_despawned_piece`) are unchanged and pass.
Order: a reload spawns the new entities, queues the hooks (one command, pairs of old and new entity), then despawns the old ones, so a hook sees the old entity alive and the new one fully drawn (`Placement`, `OfDescriptor`, `Transform`, `MountedOn`). Pairing is by id through `plan.renamed`, so a rider drawn again with its host and a renamed piece drawn again under its new id are paired, and a removed piece or one renamed and edited together is not.

## Blocked: the in-place split (build step 5)
The issue says a move, a turn, a retint or a retune keeps the entity. `crates/bevy_grimoire/tests/live_reload.rs::an_edit_respawns_only_what_changed` (line 171) asserts `assert_ne!(after["crate_b"], before["crate_b"], "a moved placement is respawned")`. A loop cannot change an existing assertion, so the item stops there; the recommendation is on #201 (change that one assertion to `assert_eq!`, then a pure move or turn updates the `Transform` in place). Until then the hook is how state survives a move.
