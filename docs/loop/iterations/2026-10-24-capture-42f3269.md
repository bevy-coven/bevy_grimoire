# 2026-10-24 capture: a still says what the picture is, and the reference stops claiming it reads the source (E-062)

Focus: bug sweep (all GitHub issues closed) · Commits: `53d3a87`..`42f3269` · Outcome: fixes only

## Summary

E-062 was filed after the previous iteration compared two captures **by their files**, got identical
bytes, and built a wrong diagnosis on it. Reproducing it showed the cause is narrower than filed
and the fix belongs in two places: our tools never said whether two pictures are the same, and our
own module doc claimed a generated reference that is in fact a hand-kept copy. `emerge_capture_still`
now returns a **fingerprint** of the picture's bytes, and the duplicated tool description is held to
the server by the ratchet that already existed — which caught this very change.

## Baseline

Gate green before and after (clippy clean; `cargo test --workspace` green). Frame time, latency and
edit-to-visible were not re-measured: the change adds one 64-bit hash per capture, tens of
microseconds against a 1.5 MB PNG, and nothing per frame.

## The bug, measured

| step | measurement |
|---|---|
| raw `bevy_debugger/screenshot {path}` | returns in **21 ms**; the PNG **does not exist** at that moment |
| the same file | appears ~200 ms later |
| read at return, after `emerge/frame_view` moved the camera | **STALE** — the previous frame's bytes |
| the same read 250 ms later | new bytes |

So the trap is real and reproducible. **But it is not our bug**: the family crate
(`bevy_debugger_mcp`, canonical repo, a pinned git dependency) documents it — its plugin README says
`screenshot` *"returns an id, and writes a file only if `path` is given"*, and its example polls
`bevy_debugger/capture {id}`. Our own `emerge_capture_still` and `emerge_snip` already do exactly
that: `grab()` polls the id with a ten-second deadline, then **writes the file itself from the
base64**, so the path it returns always exists. Verified live: file present immediately, 1,477,044
bytes, image block present.

Per the family rule ("a fix the editor needs is made and pushed there") there was nothing to fix
upstream; the gap was ours.

## Bugs fixed

### E-062: two stills could not be told apart as pictures

Fix: the answer gained `"fingerprint"` — FNV-1a, 64-bit, lowercase hex, over the same bytes that are
written to the file. No new dependency (this crate has eight and did not need a ninth for a number
whose only job is equality). Verified against the published test vector: FNV-1a 64 of `"hello"` is
`a430d84680aabd0b`.

| live measurement | result |
|---|---|
| two stills, screen unchanged | both `d1a27cbd6fd01652` |
| after `emerge/frame_view` moved the camera | `02c1004a4e92df02` — different |
| answer's `bytes` vs the file on disk | 1,517,857 = 1,517,857 |

### A second, unplanned fix: the reference lied about how it is made

While updating the tool description I found `docs.rs`'s module doc claiming **"the rendering reads
the server's own source, so there is one list"**. It does not: `docs::TOOLS` restates every
description and hint by hand, and `main.rs` states them again in `#[tool]` attributes. Editing only
`main.rs` left the generated `docs/mcp-tools.md` describing an older tool.

`docs_are_current::the_reference_names_the_servers_own_tools` **caught it** — it lists the tools
through the running server and compares each description and hint:

```
emerge_capture_still: description
  server:    "... The answer also carries a fingerprint ..."
  reference: "... The picture is returned as an image and written to a file ..."
```

So the ratchet worked; the comment was wrong about *why*. Corrected to name the copy and the test
that guards it, and `docs::TOOLS` was updated so the reference and the server agree.

## Review

An independent reviewer confirmed the FNV-1a constants against the published vectors (`""` →
`cbf29ce484222325`, `"a"` → `af63dc4c8601ec8c`, `"foobar"` → `85944171f73967e8`, `"hello"` →
`a430d84680aabd0b`), confirmed the fingerprint hashes the same buffer that is written to the file and
sent as the image, confirmed the drift ratchet really does call the running server binary, and
confirmed the added JSON field breaks no consumer. Three real gaps, all fixed:

1. **P1 — the guide's timing claim was wrong.** It said the raw call answers "about twenty
   milliseconds before the file is written". The measurement says 21 ms is how long the *call* takes
   and the file lands ~200 ms later — a tenfold understatement, and the consequence differs too: on a
   fresh path there is **no file at all**, and only a reused path yields the *previous* capture.
   Rewritten with the measured numbers and both cases.
2. **P2 — `docs.rs` failed `cargo fmt --check`.** My inserted `description:` line was indented 16
   spaces instead of 8. Fixed. The remaining three `fmt` diffs in that crate are **pre-existing**:
   `cargo fmt --check -p bevy_emerge_mcp` reports 3 with and 3 without this change.
3. **P3 — the byte-level test tested a copy.** `the_fingerprint_distinguishes_pictures_by_their_bytes`
   called a restated `fp`, not the server's function, so the server's version could have broken while
   the test passed. `fingerprint` moved into `bevy_emerge_mcp` (the library exists so tests read
   production code), the binary calls it, and the test now calls it — with the published vectors added
   so a "hash" that merely distinguishes its inputs cannot pass by accident.

Also fixed: `/// **Encode bytes into base64.**` had been left orphaned above `fingerprint` when the new
function was inserted, leaving `base64_encode` undocumented.

`docs.rs`/`main.rs` drift. No existing test or assertion was modified.
