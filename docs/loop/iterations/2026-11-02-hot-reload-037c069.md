## The case item 5 does not cover
A piece renamed **and** moved in one save is still drawn again. `renames()` pairs two rows only when they
are equal in every field and exactly one candidate exists, so a row that moved as well as changed its id
is an add plus a remove. The test named this `a_rename_that_also_moves_is_a_new_piece`, which is wrong
about the cause now that a move is identity-preserving; renamed to
`a_rename_that_also_moves_is_not_paired_so_the_piece_is_drawn_again` with **no assertion changed**.

Assumed decision (owner may override): keep the conservative pairing. Relaxing it would let two
same-descriptor rows be guessed between, and a wrong guess moves a game's state to the wrong piece —
worse than drawing it. The alternative is an explicit `alias: Option<String>` on the map row, written
when the editor renames: additive, and needing the schema-field exception, so not taken unsolicited.
