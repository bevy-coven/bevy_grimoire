# 2026-11-01 reload: a tree file that does not read keeps the trees drawn from its last good value (#200 H3 slice 4)

Focus: #200 (hot reload H3, the owner's override) · Commits: 0b3a0c9 (+ the docs commit and the release commit) · Machine: laptop (edit, commit) + big (build, test, gate) · Outcome: shipped (the issue stays open)

## Summary
A `.tree.ron` is a species: every tree of it, placed or pooled, is drawn from it. One typo in a hand edit made the species unknown in the forest view, which had already despawned every drawn tree, so the trees vanished from the viewport until the file was fixed (a log line said why). The view now holds the last good `TreeParams` of each tree file in memory, decides each file once per edit, leaves the trees standing on a refusal, and reports kind `trees` per file in `grimoire_state.reloads` with the file and the field. `tree_edit` with `set` refuses to write over a file it cannot read, naming the file and the field. A second bug the new test found in slice 1's `reload_check::field_of`: an unknown field was named twice (`undergrow.undergrow`).
