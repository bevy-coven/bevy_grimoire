## Oracle: `other:key-routing`

The one the pass of `feedback-1794024642593` named: a relation between the keys a person pressed and what the shell was sent. Mac terminals (VS Code's, iTerm2's) send `^U` for Cmd+Backspace, and `^U` is what the shell's line discipline (or readline) reads as "kill the line", so **the program sees only what was typed after the chord.** The program is `cat -v`, which prints each line it is sent:

- `cmd_backspace_clears_the_line_the_shell_is_reading` (whole application, the projects home, a real `sh`): `aa`, Cmd+Backspace, `ok`, Enter must print `ok` (and the echo of the typed line is `ok` too), where a dropped chord prints `aaok`.
- `cmd_left_and_cmd_right_move_to_the_start_and_the_end_of_the_line`: under `cat -v` there is no readline to act on `^A` and `^E`, so the line discipline passes them as characters and `cat -v` prints them spelled, `^A^E`, twice (echo and print).
- Unit tests in `terminal_view.rs`: the three chords send `^U`, `^A`, `^E` with either Command key, and nothing else does (a bare key, Command with Shift, Option or Ctrl, any other Command key).

## The fix

`terminal_view::line_editing_chord(keys, key)`: with Command held alone (no Shift, Option or Ctrl), `Backspace` is `^U`, `ArrowLeft` is `^A`, `ArrowRight` is `^E`; `type_keys` sends those bytes and still drops every other Command chord. These are what VS Code's and iTerm2's macOS terminals send, and the codes readline binds (`unix-line-discard`, `beginning-of-line`, `end-of-line`). `Option+Backspace` (the word before the cursor) already goes as `ESC DEL` through the Option-as-Meta prefix; Option+arrows are unchanged (the existing cursor-key sequences) because the note did not ask and a shell's default binding for them varies. README has a line.

Passing run on big: 210 tests (the capture's two, the unit tests, and every `terminal` and `key` test) pass; `cargo clippy -p bevy_cauldron --all-targets -- -D warnings` is clean.
