## Bugs fixed
### rules.ron of a newer version read as valid (found by the audit, not filed)
Must-fix: blocks n, common n, no workaround y: the reload verdict said `applied` and the project open then refused the file, so an edit looked landed and was not. Fixed on the way because the new acceptance test fails on it.
Root cause: `reload_check::check` ran `Rules::parse` (RON only); the version is in `validate_numbers`. Regression check: `every_format_carries_a_version::a_newer_version_is_refused_and_the_version_this_build_reads_is_named` (failed before for `rules` and `destructible_marks`, passes after).

### destructible.ron of a newer version read as this build's
Root cause: `Marks::parse` did not check the version, and `destructible_set` writes the marks back at `VERSION`. Same test. A `destructible_bake` of another version stays valid: it is a cache, stale and baked again.

## Review
My own review before the push, the five questions: (1) does the `rules` check now refuse a file the editor opened before? it runs the same `validate_numbers` the project open runs (`project_data.rs:138`), and the frozen 0.1.0 and 0.3.0 rules files still read (`old_data`). (2) does `Marks::parse` refuse anything a build writes? it writes `DESTRUCTIBLE_VERSION` only. (3) can an entry of REBUILD be wrong? each was checked against the code (the editor's cargo features, `ops::registry`, `keys::BINDINGS`, `chrome` constants); the game crate has no features, so `family_crates` says "of the editor". (4) is a test pinning an incidental detail? the reason-length floors (8 words) are the only soft check, and exist because the issue asks for a reason per entry. (5) the guide counts (18, 11, 4) are prose and not rendered; the tests hold the lists.

A `reviewer` subagent then ran over 2935a4b after the push (the first draft of this report said it had not run; that was written before I spawned it). It confirmed the `rules` change (project open, the game and the MCP server all already run `validate_numbers`; the frozen files pass), the counts (33 kinds = 18 + 11 + 4; none of the 11 carries a `version`) and the REBUILD claims, and found one P1 and two P3s. **P1**: `Marks::parse` is called only by the reload check; `destructible_set` and `destructible_hit` read the marks with `read_named`, which is plain RON, so a version 2 file was still taken and written back at version 1, the failure my answer to (2) and the commit message said was fixed. Fixed forward in the next commit: `ops_destructible::load_marks` refuses a version it does not read (naming `destructible.ron (version)`, the bytes stand) and the dead `marks.version = VERSION` is gone; the new editor test `a_destructible_file_of_another_version_is_refused.rs` failed before and passes after (built with the `bevy_carnage` feature, which the push gate does not build). **P3, taken**: the test matches the version the build reads as a whole number (`names_number`), not as a substring. **P3, not taken**: `DESTRUCTIBLE_VERSION` is one constant for the marks and the bake, so bumping it to force a re-bake would now also refuse every marks file; split it into a marks version and a bake version when a bake changes shape.
