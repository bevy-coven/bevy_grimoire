## Bugs fixed
### #317: a click on the terminal does not give it the keyboard
Must-fix: blocks y (clicking is how a person types into a pane), common y, no workaround n (Ctrl+`).
Root cause: `PointerClick` bubbles. The two global observers (`a_click_takes_the_keyboard`, `a_click_elsewhere_gives_it_back`) each read the hop's own entity, so a click on the body took the keyboard on the first hop and gave it back on the hop at the frame root above the pane. Now both act once, on `click.original_event_target()`.
Regression check: `a_click_puts_the_keyboard_in_the_terminal::*` (bevy_picking's own move/press/release on the surface image). Failed before: "a click in the terminal's body did not put the keyboard in the shell", and the same for the bar.

### #318: Ctrl+D in the shell also opens the developer report
Must-fix: blocks y (EOF is how a person ends `cat` or leaves a shell), common y, no workaround y.
Root cause: `report_key` read Primary+D from `ButtonInput` with no regard for the terminal. Now `TerminalFocus::owns(chord)`: while the shell has the keys, a chord on Ctrl is the shell's control code; a chord on Command (mac) stays the window's. Assumed decision (recorded on #318): the rule applies to every window chord spelled on Ctrl, VS Code's terminal-skips-shell rule in its smallest form; measured, it was the only window chord that needed it: every `keys::BINDINGS` chord and the command palette's Ctrl+K already stand down on `Context::Typing`, which `editor::sense_context` sets while the terminal holds the keys; the report read `ButtonInput` raw and was the one outside that gate.
Regression check: `the_shell_keeps_its_ctrl_chords::ctrl_d_ends_a_cat_in_the_shell_and_opens_no_report` (failed before: "Ctrl+D typed into the shell opened the developer report over it"); `the_report_chord_still_opens_a_report_when_the_editor_has_the_keys` guards the old behaviour.
