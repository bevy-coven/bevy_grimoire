# 2026-11-01 reload: a notes file that does not read keeps the notes shown, and notes and family settings report a verdict per edit (#200 H3 slice 5)

Focus: #200 (hot reload H3, the owner's override) · Commits: 20872c1 (+ the review-fix commit and this report's commit) · Machine: laptop (edit, commit) + big (build, test, gate) · Outcome: shipped (the issue stays open)

## Summary
The note signs and the Notes panel each read `<map>.notes.ron` themselves and took an empty list when it did not parse, so one bad hand edit made every sign and row vanish until the file was fixed. One view (`notes_view::NotesView`, synced by `sync_notes_view`) now holds the last good `Notes`, decides each edit once and reports kind `notes` with the file and the field in `grimoire_state.reloads`. The family host's `reload_settings` reports kind `family` (applied, refused, gone) the same way, so an agent over BRP can ask whether a settings edit landed.

Design: the view looks at the file every frame by size and modification time and once a second regardless (two writes inside one coarse timestamp tick look alike), keeps the last text read (good or refused) so the same bytes are decided once, forgets the verdict of a deleted file and starts afresh for another map. For family settings `FamilyWatch` (core) reports a change from the settings in force and its own test pins that restoring the last good text is no change, so the mapper settles refused files against the disk twice a second (`settle_refused`), names files broken before launch (`unread_at_launch`) and decides the same bad bytes once.
