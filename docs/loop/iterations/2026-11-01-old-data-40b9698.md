## Summary
Build step 5 of #200 asks for a rule that refuses a settings struct which adds a field with no default, or removes a field old data needs. Nothing checked it: every existing test reads a value the current type has just written, so a required field added to `Standards` left every test green while every project on disk stopped reading. `crates/bevy_grimoire_core/tests/old_data/` now freezes one file of every kind `reload_check::check` reads (22 kinds, 23 files), as a release wrote it, and `tests/old_data.rs` reads each with the type's own reader and refuses the edit naming kind, file, field and release.

## Enhancement: a frozen corpus of old data (step 5)
Goal: a settings type that no longer reads what an earlier release wrote is refused, naming the field, before it ships.
Files: new `crates/bevy_grimoire_core/tests/old_data.rs` and `tests/old_data/core-0.1.0/` (7 files, byte for byte from tag `bevy_emerge_core-v0.1.0`: kits, vocab, a library, two policies, compositions, rigs) and `tests/old_data/core-0.3.0/` (16 files, written once by the current code for the kinds the first release had no sample of); `docs/guide/reload-contract.md` (a paragraph).
Proof, failed before: with `pub review_m: f32` added to `Standards` (no default, and `Default` updated, as a developer would), `tests/reload_verdicts.rs` passes (8 tests) and the new test fails: `standards (standards.ron) written by core 0.3.0 no longer reads, at field review_m: standards: parse: 4:1: Unexpected missing field named review_m in Standards`. On the base there is no such test, so the same edit ships. After, with the mutation reverted: 3 of 3 pass, and the 0.1.0 files, which no one had read since the release, all still read with today's types.
Design: why a corpus and not a derived schema. A type cannot be asked which fields have a default without a value of it, and a value the current code writes always has the new field. Old data is the one input the edit cannot update, and frozen files under `tests/` are protected, so the loop cannot reword them to pass. The first release's files are real old data (written by `bevy_emerge_core` 0.1.0's editor), not a copy of today's. A removed field fails only for a type with `deny_unknown_fields`; a type that ignores unknown fields reads the old file and loses the field silently, which this rule does not catch.
MCP: none.
