### B-044: the Linux CI run fails with a load-dependent flake (new, open)

Judgment: 2 of 3. Blocks: no (`main` is green). Common: yes (44 of 120 runs fail under the stress below). No workaround: yes (a CI retry is not allowed: it would hide a real double-apply).

- Test: `crates/bevy_emerge_mapper/tests/one_undo_takes_back_the_newest_change.rs::cmd_z_after_a_resize_takes_back_the_resize_and_not_an_older_edit`.
- Failing assertions: `:138` "the second Cmd+Z did not take the run back" (left 4, right 0); `:145` "the first redo did not put the run back" (left 8, right 4). At `:145` the map data holds 8 placements.
- CI: red on `ab5ebf8` (run 39926254825); green on `f36ee00` (run 39906306802) and `b99c056` (run 39935647016).
- Stress: 8 concurrent `xvfb-run` workers pinned to `taskset -c 0,1`.

| Commit | Failed runs |
|---|---|
| `f36ee00` | 44/120 (30 in the panic tally: 20 at :138, 10 at :145) |
| `ab5ebf8` | 67/320 |
| either, single process on 1–2 cores | 0/300 |

`f36ee00` is an ancestor of the cycle 5 merge `ca6d1ef`, so the flake was in the tree before cycle 5. The bisect premise of "introduced in cycle 5" is false.

Ruled out:
1. Duplicate Undo/Redo handlers. One each: `keys.rs` 1284/1294, called from `editor.rs` 7053/7058.
2. A `Placement` marker split. Inserted through the same `Commands` as the spawn at every site.
3. A key-context race. `sense_context` runs in `Phase::Sense`, before `Act`.
4. Time-based key repeat. Undo and Redo use `keys::just_pressed` (`keys.rs` 3354). `TimeUpdateStrategy::ManualDuration(600 ms)` left the rate unchanged (26/120).

Open: the undo stacks and the `apply` path under scheduling. `undo()` (`editor.rs` 7482) and `redo()` (7509) pop, call `apply`, and push the inverse. The suspect is `apply` for `Undo::Added` / `Undo::Moved` (`editor.rs` ~7726–7813): it drains `open.map.placements` synchronously and despawns by `Placement` id through deferred commands. `Stranded` is returned after the map has already moved, when `heights()` fails.

Next step (about 15 min on big): log `undo_len` / `redo_len` and the placement count inside `undo()` and `redo()` under the stress. That separates "the second undo never popped" from "the redo applied twice".
