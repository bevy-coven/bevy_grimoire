# 2026-11-01 reload: a damaged destructible marks file or bake is named with its file and field and never overwritten (#200 H3 slice 11)

Focus: #200 (hot reload H3, the owner's override) · Commits: d47626b (+ aaf33af changelog and backlog, release d25558a, and this report's commit) · Machine: laptop (edit, commit) + big (build, test, gate, release) · Outcome: shipped (the issue stays open)

## Summary
`destructible_set` read `destructible.ron`, changed one piece and wrote the whole file back, and `destructible_hit` read it and the piece's cached bake. The marks file read with the parser's position and no field, and a bake that did not parse was baked again over the damaged bytes with no word. The two files' schemas (`Marks`, `Chunk`, `Bake`) were private to the mapper behind the carnage feature; they now live in engine-free `bevy_grimoire_core::destructible`, so `reload_check::check` reads both kinds in every build and the registry's three-bad-files table holds them. `destructible_set` (when it marks) and `destructible_hit` refuse a file that does not read with `destructible.ron (pieces)` or `destructible/site__cart.bake.ron (chunks[1].points)`, say it is left as it is, and write nothing.
