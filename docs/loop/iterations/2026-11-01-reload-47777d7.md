# 2026-11-01 reload: a damaged line of oplog.jsonl is named with its line and field (#200 H3 slice 9)

Focus: #200 (hot reload H3, the owner's override) · Commits: 47777d7 (+ this report's commit) · Machine: laptop (edit, commit) + big (build, test, gate) · Outcome: shipped (the issue stays open)

## Summary
Every reader that walks `assets/grimoire/oplog.jsonl` (the steps feed, `grimoire/oplog_read`, the after-edit queue) skips a line that is not an entry, so a hand edit or a write cut short cost the author what that line recorded and said nothing: the journal counted "line(s) of the log could not be read" with no line and no field, and the undo walk refused without naming the field. Core gains `reload_check::read_lines` (a JSON-lines reader that names the first damaged line as `line N.<path>`); `oplog_view::sync_oplog_view` decides each look at the log into `grimoire_state.reloads` as kind `oplog`, only when what it found differs from the look before; `ops::undo_target` reads the log with the same reader.

## Found, not fixed (outside this slice)
`ops::append` writes `{line}\n` at the end of a file that may not end with a newline, so after a write cut short the next operation's line is glued to the torn one and both are skipped by every reader: one more entry lost than the crash cost. The verdict now names the glued line (`line N`, trailing text), but the append should write a newline first when the file does not end with one. It is a change to the dispatcher, not a reload kind, and it is from reading the code, not run: filed as #206, a bug that waits under the hot-reload override.
