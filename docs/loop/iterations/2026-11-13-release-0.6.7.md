Tag `bevy_cauldron-v0.6.7` on `cc05ab5a`. Gate 3978/3978 (`7c7d67e9`). macOS workflow run 43445885806: **success**. Published to crates.io: `bevy_grimoire_core` 0.11.0, `bevy_grimoire_rhai` 0.1.1, `bevy_grimoire` 0.5.1. Tags: `bevy_grimoire_core-v0.11.0`, `bevy_grimoire_rhai-v0.1.1`, `bevy_grimoire-v0.5.1`.

## This is the second try, and the first one failed

0.6.6 was cut earlier the same day (`d7f783d9`; core 0.11.0, rhai 0.1.0, grimoire 0.5.0 published) and its macOS app build **failed**:

```
error[E0308]: mismatched types  --> crates/bevy_grimoire_rhai/src/lib.rs:686:71
  Dynamic::from_float(f64::from(delta_s))  expected `f32`, found `f64`
```

`rhai::FLOAT` is `f64` unless rhai's `f32_float` feature is on, and cargo unifies features across the whole graph. The release app is built with `cargo build -p bevy_cauldron --features family_all`, which pulls in a crate that turns it on. Our gate never builds that graph, so it passed 3978/3978 and the first build that failed was the release. Three sites assumed `f64`. `91321ce7` converts through `FLOAT` instead and was verified with `cargo clippy -p bevy_grimoire_rhai -- -D warnings` under default features **and** `--features rhai/f32_float`.

**Nothing was yanked.** `bevy_grimoire_rhai` 0.1.0 and `bevy_grimoire` 0.5.0 are on crates.io with the same flaw; the standing rule is to fix forward, so 0.1.1 and 0.5.1 carry the fix and `bevy_grimoire` now floors `bevy_grimoire_rhai` at 0.1.1, so no resolver picks the broken one. 0.6.6's tag stays where it is and is a release that never produced an app.

A second failure followed: the 0.6.7 run compiled (the fix worked) and then died with `dist/Cauldron.app: internal error in Code Signing subsystem`. mac_air's disk was 100% full (268 MB free); 0.6.5 had signed fine with room. Removing my own release scratch (`~/.cargo/rel-target`, 1.8 GB, and the `/tmp/rel-066` worktree) and re-running the workflow on the same tag succeeded. The 38 GB cargo target of the release runner and the 79 GB shared target on mac_air are not mine and are untouched: **mac_air is still at ~2 GB free, so the next release will hit this again** unless the owner reclaims space there.

## What `bevy_grimoire_core` 0.11.0 breaks

`cargo semver-checks check-release -p bevy_grimoire_core --baseline-version 0.10.3`: *semver requires new major version: 6 major and 0 minor checks failed.* All six are the RON cutover's deliberate removals: the `migrate` and `ron_surgery` modules, `migrate`'s `Report`, `Converted` and `Unplaced`, a removed const, and `reload_check::read` taking 4 parameters instead of 3. Before 0.1.x a pre-1.0 minor carries that. `bevy_grimoire` against 0.4.9: *no semver update required*. `bevy_grimoire_rhai` had never been published; 0.1.0 was its first release and 0.1.1 its first working one.

I killed those two processes; the worker then made children close every fd above 2, take their own process group and `PR_SET_PDEATHSIG`, and #412 shipped with a gate test (`a_spawned_child_holds_nothing_of_its_parents`) so it cannot come back unnoticed.

- **bmb is not usable for builds right now.** Its disk fell from 18 GB to 126 MB under one worker build while another agent's `cargo test` was compiling Bevy beside it. 17 GB of that was my own finished `~/.cargo-target-fleet/design`, which I removed; the 181 GB `~/.cargo-target-shared` and 121 GB `~/llm` are other agents' and untouched.
