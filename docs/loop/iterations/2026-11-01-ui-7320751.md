# 2026-11-01 ui: a right-click on a placed piece opens its menu (UI-36 slice 1, #230)

Focus: ui · Commits: 3da0f1f, 7320751 · Machine: big · Outcome: shipped (slice; #230 stays open)

## Summary
The gooey pin moves to 15116c1 (G-06, #10 closed as completed). A right-click on a placed piece opens one gooey `context_menu` at the pointer: Turn left, Turn right, Tip about x, Tip about z, Lift, Lower, Remove. Each item is the key's own verb on that piece by id through the registry (`editor::piece_verb`), so Remove is one `placement_remove` line and one Cmd+Z. `turn`, `tip` and `lift` were split into a find half and an `*_at` half the menu shares.

The headless tests passed while the live editor had no menu: a `Startup` spawn is despawned by the door change (`screen::close_the_door`), so the menu is spawned `OnEnter(Screen::Editor)`. No test can see that (the harness never leaves the screen); the clip and the live run are the proof.
Decision recorded: gooey's context-menu click, popover anchoring and closing live in `GooeyNavPlugin`, which the editor had left out ("the editor owns the arrow keys"). It is added: its arrow handling acts only on widgets with `AutoDirectionalNavigation`, which the viewport is not. UI-35 (focus regions, waits on G-23) owns the rest. The 5280-line keys census and 986 editor tests pass with it.
The pieces have no colliders, so the right-click is found with `under_cursor_target` (the keys' own rule) and sent to gooey as the secondary `PointerClick` its guide names for a host that picks for itself.
