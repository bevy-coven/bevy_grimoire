# feedback-1793928159971 — the hover highlight is 38.5 logical px below the pointer

**Classification:** `bug`. *"When mouse hovering over these items, the highlighted item doesn't match where
the mouse is pointing"* describes the screen as it is.

**Outcome:** `blocked` — **reproduced from the record**, not testable in this harness. The pass's lasting
product is a correction: the coordinate-space rule the last two passes got backwards.

## The report

| | |
|---|---|
| note | *"When mouse hovering over these items, the highlighted item doesn't match where the mouse is pointing."* |
| pick | `? › MenuBar › MenuTitle › MenuPanel`, rect `[427, 68, 1023, 1587]` physical |
| window | 2560x1604 physical, 1280x802 logical, `scale_factor` 2, `ui_scale` 2.4 |
| app | 0.2.7 recorded; **0.2.9** installed on mac_air |

**Units.** `at` = `733.3, 694.7` surface falls inside `rect`, and `366.6, 347.3` logical falls inside
`rect ÷ scale_factor`. Both valid → **ambiguous** on this record; it is resolved below.

## Reproduced, measured from the frame

Scanning a clean column inside the menu for the hover band:

```
highlight bands (physical y):  (78, 133)    -> the focus ring on the first row
                               (748, 796)   -> the hover band, centre y 772
recorded pointer             :  physical y 694.7
```

The highlight sits **77 physical px (38.5 logical) below the cursor**. Not rounding: most of a row, which is
exactly what the note describes.

## The coordinate-space rule, measured — and the correction

Measured on the running 0.2.9, aiming at the toolbar's `Place` option, whose `ComputedNode` centre is
`(82.5, 175)`:

| injected cursor | what became `Hovered` |
|---|---|
| `(82.5, 175)` | **nothing** |
| `(41.25, 87.5)` | the control centred at physical `(82.5, 175)` |

So **`ComputedNode`/`UiGlobalTransform` report physical pixels; the injected cursor takes logical**. Converting
once, `/ scale_factor`, is correct; skipping it is off by exactly 2 here — the same magnitude as the offset
this capture reports, which is why it matters.

**This corrects `feedback-1793927950267` and `feedback-1793928048623`.** Both recorded that "the injected
pointer never establishes a pick" and blamed the editor. It does establish a pick. The misses were mine. All
three rows now say so in the ledger.

## Why it is blocked, not fixed

Two attempts at the whole-application test, and both failed for **harness** reasons worth recording so no
later pass repeats them:

1. **`DebugCursor` does nothing headless.** `view::sense_pointer` reads the window first
   (`Some(w) => cursor_position(w, &injected)`) and answers `None` without a `PrimaryWindow` — honestly, since
   the pointer must be converted into the surface's space. My first test had no window, so the pointer never
   moved and **one node stayed hovered across every iteration** — which is why its output read
   `pointer at (84.6, 701.2) hovered a node centred at (145.4, 350.0)` for rows 30 px apart.
2. **`Hovered` is not driven the way I assumed.** The crate's own injected-pointer test
   (`an_injected_pointer_over_a_dock_is_pickable`) asserts on `PointerLocation` for a **divider**, not on
   `Hovered` for a list row. So the harness has no route to "which row is highlighted".

Per the budget rule — two failures at the same step — the pass stopped building there and shipped nothing.
