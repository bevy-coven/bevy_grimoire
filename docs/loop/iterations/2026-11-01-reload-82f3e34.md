# 2026-11-01 reload: the last two kinds, a referenced picture and a family settings file, are refused naming file and field (#200 H3 slice 12, closes #200)

Focus: #200 (hot reload H3, the owner's override) · Commits: 82f3e34 (+ the changelog line 23b00b4, the release b306eed, this report's commit) · Machine: laptop (edit, commit) + big (build, test, gate, release) · Outcome: shipped (#200 closed)

## Summary
Two kinds had no reader that names the file and the field. `reference_images` (a picture an agent is told to look at) was never read here, so a file a full disk cut off, a text saved over it or another format renamed looked fine until an agent opened it. A family settings file was `applied` as soon as it was valid RON, and the crate's own type refused it later on the status line, so `grimoire_state.reloads` said a file landed that the crate had thrown away. Core gains `image_header::read` (PNG, JPEG, GIF and WebP headers, no image crate; a refusal names `signature`, `format`, `header`, `width`, `height` or `extension`); the editor gains `reference_view::sync_reference_view` (the open map's pictures, by size and modification time and once a second, one verdict per edit as kind `reference_images`) and `family_host::read_as` (a settings file is read as `ElementsSettings` or `GooeySkin` before it is taken, so a refusal names `family/<crate>.ron` and the field, is said once, never reaches `FamilySettings`, and the previous settings stay). With these two every kind in the registry names its file and field when it does not read; the mapper's ratchet of kinds nothing reads is empty.
