# feedback-1793928091805 — menu shortcuts: a `?` and a ragged column

**Classification:** `bug`. *"The shortcuts have a "?" in the middle… But they also don't look aligned
vertically"* describes the screen as it is.

**Outcome:** `blocked` — and the pass's real product was **correcting three rows** that had blamed the
editor for a limitation of the harness.

## The report

| | |
|---|---|
| note | *"The shortcuts have a "?" in the middle, not sure what's up with that? But they also don't look aligned vertically."* |
| pick | `? › MenuBar › MenuTitle › MenuPanel`, rect `[118, 68, 555, 326]` physical |
| window | 2560x1604 physical, 1280x802 logical, `scale_factor` 2, `ui_scale` 2.4 |
| app | 0.2.7 recorded; **0.2.9** installed on mac_air |

**Units.** `at` = `395.6, 106.5` surface falls inside `rect`, and `197.8, 53.2` logical falls inside
`rect ÷ scale_factor`. Both valid → **ambiguous**; both were tried when driving.

## The two claims are two different things

1. **the `?`** is the tofu box already filed as `bevy-coven/bevy_gooey#45` from
   `feedback-1793927744511`: the Mac chord spelling `⌘⌃⌥↩⎋⇥` is not in the face Cauldron ships, and Bevy's
   `system_font_discovery` is off, so there is no fallback.
2. **the alignment** is *not* a layout fault. gooey builds the row as `[mark, label, shortcut]` with
   `Role::MenuText { flex_grow: 1.0 }` and `Role::MenuShortcut { flex_shrink: 0.0, margin-left: 2 gaps }`
   (`src/skin.rs:3633` and `:3674`) — a right-aligned column by construction. A tofu box is **wider than the
   glyph it replaces and a different width per codepoint**, so `↑?Z` occupies more advance than `?Z` and `?`
   alone less: the column is ragged because the *widths* in it are wrong, not because the alignment is.
   Fix gooey#45 and this half goes with it.

## The attempt

| `mac_air` | metal | 2560x1604 | 2.4 | **not reproduced** — clicking `Edit` (tried at both logical 83.5,16.5 and physical 167,33) left every `MenuPanel` at `display: None`, so no menu opened and the column could not be measured |

## What the pass actually found

**The pointer injection does not establish a pick on this build.** Measured on the running 0.2.9:

```
MenuTitle + Hovered  →  10 rows, all false     (while the frame shows one title lit)
Cmd+O over the same transport  →  screen editor → project
```

So the cursor **moves** (the screenshot's highlight changes) but nothing is ever hovered or clicked, while
**keyboard injection works from the same call**. That isolates the fault to the pointer path of
`bevy_fairy/input`, not to the editor.

This matters because the two previous passes recorded the opposite: `feedback-1793927950267` and
`feedback-1793928048623` both blamed *"clicks do not reach the button"* on the product. That was the
instrument. Both rows are corrected, and what survives is what was measured:

- `…950267`: a synthetic `Activate` on the `NavTab` **does** switch the page, so the handler is correct —
  which was always the useful half of that row;
- `…048623`: the frame **does** show the Pieces panel overflowing, so `seen, not testable` still stands.

## What this repo did

- Took the capture, triaged it `bug`, recorded the attempt.
- Established the two claims' separate causes, and that the alignment follows from the tofu.
- **Corrected** the reasons on two earlier rows rather than leaving a false product bug in the queue.
- Shipped no test (nothing failed on the base commit in a way that isolates the defect), no fix, no
  changelog line.
