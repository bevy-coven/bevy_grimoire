# feedback-1793927950267 — the What's new tab does nothing when clicked

**Classification:** `bug`. *"The "What's new" button here is not working?"* reports that pressing it fails,
which is how the thing behaves rather than how it should.

**Outcome:** `blocked`, and honestly so: the defect is **reproduced**, the obvious suspect is **eliminated**,
and the cause was not isolated before the pass ran out of budget. No fix is claimed and nothing was shipped
for this capture.

| | |
|---|---|
| note | *"The "What's new" button here is not working?"* |
| pick | `projects home › Split › SplitPane › Surface(1)`, rect `[0, 0, 576, 1604]` physical — the whole sidebar pane, not the tab |
| window | 2560x1604 physical, 1280x802 logical, `scale_factor` 2, `ui_scale` 2.4 |
| app | 0.2.7, screen `launcher` |

## Reproduced, by pixels

On the Projects home, clicking the sidebar's `What's new` tab leaves the screen unchanged: the page heading
still reads **Projects**, the **Projects** tab keeps its selection rail, and no page changes. Before/after
stills: `/tmp/wn_before.png`, `/tmp/wn_after.png` on `big`.

| host | backend | window | ui_scale | outcome |

| `big` | vulkan | 1280x720 | 1.2 | **reproduced** — the page does not change |

## What is eliminated

**The click handler is correct.** `pressing_the_whats_new_tab_shows_the_whats_new_page` builds the home with
real plugins, triggers `bevy_gooey::Activate` on the `NavTab` entity, and the page switches — it passes on
the base commit. `show_the_tab` also reads correctly: it writes `Display` from `page.0 == launcher.tab` and
moves `Selected` to the chosen tab.

So the failure is **between the mouse and the button**: the press is not reaching the tab's `Activate`. That
is a hit-test question, not a logic one.

## What is not established, and what the next pass needs first

Which entity the pointer actually hits, and whether some node above the tab swallows it. The instrument for
that is BRP — and **it cannot see any of the launcher's pieces**: `NavTab`, `Launcher`, `LauncherRoot`,
`SidebarRoot` and `HomeContent` are none of them `Reflect`, so `world.query` and `world.get_resources` answer
nothing for them. I hit this mid-pass and misread it at first as "the launcher built no tabs", which it does
not mean.

**So the first move next time is not a hypothesis, it is instrumenting the read**: derive `Reflect` on the
launcher's marker components and the `Launcher` resource (with `register_type` in `LauncherPlugin`), then
`world.query` can name the entity under the cursor. That is a small, safe change and it makes this capture
tractable; it is also the same blindness that cost a pass on `feedback-1793927744511`-adjacent work.

## What this repo did

- Reproduced it and recorded the attempt.
- Built the regression test `capture_feedback_1793927950267`, which passes on the base commit and therefore
  proves the *handler* is fine — kept because it is the boundary of what is known, and it is the test the
  eventual fix must keep green.
- Set the capture `blocked` with the above in `reason`.
- Shipped no fix: a fix for a click path nobody has watched fail in the source would be a guess, and the
  command file's rule is to stop rather than reason toward one.
