## Specification

`bevy_gooey` has had the widget since v0.45.0 (`led(label, state)`, gooey#80, asked for by #343): a dot with four silhouettes (hollow ring `off`, disc `live`, rounded square `busy` with a pulsing glow, diamond `failed`) and its state in words, so colour is never the only signal (WCAG 1.4.1) and the pulse stops under reduced motion. The editor was pinned at v0.43.1, two minor versions short of it. #343's assumed reading was taken as written: the LED is the agent's connection, **lit and steady when an agent tab's checks all passed or were skipped (`live`), pulsing amber while a check waits (`busy`), red when one failed (`failed`), dark with no agent tab (`off`)**, in the terminal's bar before the status chip and staying after the card goes.

The protected tests pin the card's `Text` children (`OK Agent started…`, one line tall, heading first), so the card's rows were left as they were and the LED is a **foot row** of the card (a non-`Text` child), not a replacement for the rows' marks.

## The cause was not only here: a gooey regression found by the pin move

Moving the pin to v0.45.1 made **26 of the editor's tests fail** on big, all of them tests that click or wheel over the map (`a_click_outside_the_viewport_places_nothing`, `a_piece_lands_where_the_pointer_is`, `a_person_removes_a_piece_and_undoes_it`, the right-click menu, shift-click selection, the wheel test of feedback-1794147411369, and the others). The cause is in `bevy_gooey` v0.44.0 (G-62, the collapsed pane's peek): **`split_pane` put a `Hovered` on every pane**. This editor, like any host that tells the interface from the world behind it, reads "a node with `Hovered` is interface" (`view::over_ui` takes every node that carries the component, whatever its value), so a pane that holds the map's viewport takes every click meant for the map as a click on the interface. (That the viewport stands in such a pane is read from the code and from the fix's effect: with the pane's `Hovered` gone all 26 pass. It was not stepped through in a debugger.)

Fixed in `bevy_gooey`, in its own commit with its own test, and not patched or worked around here (`dark-incorporated/bevy_gooey` `d1ec9ee`): `update_split_peeks` inserts `Hovered` on the first pane when it first sees the split collapsed and removes it when the split is not; an open split's panes carry none. `tests/split_pane_hover.rs`: both tests fail on `5ffe9cd` (*the first pane of an open split carries no Hovered*, `tests/split_pane_hover.rs:142`, and the collapsed-split test at `:158`) and pass on the fix. Its suite (lib and tests, all features, fmt clean, doctests 269 passed) ran 1277 tests and **1276 passed**; the one that failed, `elevation::each_surface_casts_its_heights_stack_from_the_skin`, asserts a toast is "still fading in", which is a wall-clock condition, while big's load average was 60 to 110. It passed on its own at both the parent (`5ffe9cd`) and the fix, so it is not this change; why it failed once was not investigated further.

With the gooey fix on the path the editor's **whole suite passes: 1982 tests, 0 failed** (`bevy_cauldron`, run on big with the dependency pointed at the gooey worktree), so versions 0.46.0 to 0.52.1 brought no other break the editor's tests can see. The pin is now `d1ec9ee` (gooey 0.52.1 and the fix).
