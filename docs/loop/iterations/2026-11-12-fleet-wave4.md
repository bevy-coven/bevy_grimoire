## What the reviews caught

Both clusters were sent back at least once, and in each case the worker's own "verified" claim was wrong.

**#411 (bench)**: the worker's first DONE pointed at a crate with **zero tests** — `cargo nextest run -p bevy_cauldron_bench` printed `0 tests run` and then `error: no tests to run`. Then a reviewer found two checks that let a wrong run *pass*: `placement_near_wall` used `gap.abs() <= max_gap_m`, so a bed 3 cm **through** the wall passed; and `no_problem` passed on an unreadable map because the snapshot substituted `Map::default()`. Both are fixed, with `a_piece_sunk_into_the_wall_fails_the_near_wall_check` and `an_unreadable_map_fails_the_map_checks`. The crate now runs 11 tests, all passing.

**#400 (design)**: a reviewer found four MUST-FIXes — the Owner exceptions were written inside the test files instead of the commit body; an oversize file was reported as "32769 bytes" whatever its real size; the chain limit summed a topic across the whole tree (12 regions of 6,144 bytes refused although every real chain is 12,288); and the `pulldown-cmark` justification cited a `bevy_gooey` Markdown module that does not exist. All four fixed, plus all four NITs. Then the gate found a fifth the worker's suite had not: the new `design` reload kind is not on the `STILL_UNCHECKED` ratchet in `a_file_that_does_not_read_is_never_overwritten.rs`, so the gate failed on a test no round had run. Sent back.

The pattern is the same both times: a worker verifies the crate it touched and reports DONE, and the tests the *merge* and the *workspace* bring are never run. It is the same failure the YAML cutover had twice.

## The gate, and why it was dying

The gate was killed by `systemd-oomd` **ten times** in four hours. It was not the gate's own appetite. `ps` showed **two GitHub Actions containers for `foundation_vs_slop`** at `CARGO_BUILD_JOBS=8` each, `hs-distill-serv` holding 5.3 GB, and `/tmp` — a 16 GB tmpfs whose pages live in swap — at 84% full. Two `gate-retry.sh` loops had also started and raced, restarting each other's builds.

What worked: one gate in one detached unit, `CARGO_BUILD_JOBS=1 NEXTEST_TEST_THREADS=2`, `MemoryMax=8G`, the bench worker paused while the gate ran, and the fleet's own stale worktree removed from the tmpfs. Both gate runs then completed at 673 s.

One test flaked twice under that load and passes alone (5/5 in 0.54 s): `compose_cursor_is_an_operation::a_held_arrow_writes_one_line_and_still_walks_every_repeat`. Logged on #322 with its measurements. A docs-and-media commit cannot have caused it.

## Owed by the owner

**#401's protected tests.** SG-02's Decision says `trust::GuideGrant` becomes `TextGrant { project, path, sha256 }` and `TRUST_VERSION` is bumped, and that the old store's frozen file is added to `tests/old_data.rs`. That breaks two protected assertions by construction (`a_projects_guide_needs_the_persons_trust.rs:174` — a struct initialiser missing `path`; `:142` — `assert_eq!(TRUST_VERSION, 2)`), and the frozen list is a third. The worker correctly refused and stopped, rather than building half a slice that would leak a cloned project's prompt text. The manager's recommendation is to grant the exception, because the issue asks for one store and one question rather than two.
