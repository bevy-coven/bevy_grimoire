# The bevy_grimoire MCP tools

Generated from the server's own tool declarations. **Do not edit this file** — it is written by `cargo run -p bevy_grimoire_mcp -- --emit-docs`, and a test fails when it does not match the server.

The server speaks the Model Context Protocol over **stdio**, and reaches the running editor over the Bevy Remote Protocol on `BEVY_BRP_PORT` (default 15702). It writes nothing to disk itself: the editor owns the project directory, and every file the editor writes is written by the editor.

## Working a note

A person leaves notes on the map (a rectangle or picked pieces, with an instruction) and presses Send. Any agent connected to this server can work a sent note; the editor holds no agent logic. If the project's `agent.ron` names a command, Send also starts it once per Send (`(version: 1, command: Some("omp"), model: "claude-sonnet-5-5")`; `args` may use `{model}`, `{prompt}`, `{project}`; the default arguments are `-p --model {model} {prompt}`). With no `agent.ron`, or no `command` in it, Send only queues the notes, and a hand-started agent works them the same way.

1. **List.** `grimoire_state` has a notes section: the sent and claimed notes with `id`, `holder` and `lease_until`. Pass `note=<id>` for a note's bundle: text, area and margin, nearby pieces, the palette, the camera and earlier notes.
2. **Claim.** `note_claim` with your name as `agent` holds the note for a lease. `note_renew` keeps it while you work, `note_release` gives it back. A note another agent holds is refused.
3. **Work inside the fence.** Every `grimoire_apply_operation` you make with `agent` set is checked against your note: an operation reaching outside the note's area plus one cell is refused before anything is written. Removing a piece a person placed is refused until you have asked with `note_ask` and the person has answered with `note_answer`. Capture a before and an after still with `grimoire_capture_still`.
4. **Resolve.** `note_resolve` closes the note with a one-line `summary`, your `assumptions`, the `ops` (operation ids) you ran and `captures` `[before, after]`. The person then keeps the result or undoes the whole note in one step, which reopens it.

Worked example: the person's note `n1` covers cells 0,0 to 2,2 ("tidy the wall"), and the agent `omp` works it. Operations, one per line:

```json
{"operation": "note_add", "parameters": {"cells": [0, 0, 2, 2], "text": "tidy the wall"}}
{"operation": "note_send", "parameters": {}}
{"operation": "note_claim", "parameters": {"id": "n1", "agent": "omp"}}
{"operation": "placement_add", "parameters": {"piece": "site/wall", "at": [0.5, 0.5]}, "agent": "omp"}
{"operation": "note_resolve", "parameters": {"id": "n1", "agent": "omp", "summary": "added a wall", "captures": ["before.png", "after.png"], "assumptions": ["the wall belongs in the corner"]}}
```

The first two lines are the person's (the note box and Send); the rest are the agent's. `placement_add`'s piece and cell are the example's own: use pieces from `grimoire_list_pieces`.

## The tools

### `grimoire_present`

Put a result in front of the person: a title, a one-paragraph summary, what they specified, what you inferred, up to three places worth checking, and the operation ids it covers. The editor shows it as a question: Keep, or Undo all (which undoes every listed operation, newest first). This call returns at once; read the person's answer from grimoire_state's presentation.answer ("kept", "undone", or why the undo stopped). It does not change the map by itself.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | false |
| `idempotentHint` | false |

### `grimoire_list_operations`

Every operation the running bevy_grimoire editor knows, with each one's parameters' JSON schema and how it is undone. Call this before grimoire_apply_operation so the parameters are the ones the operation actually takes. Returns the list; it does not change anything. The undo column names the strategy an operation declares; grimoire_undo_operation performs it. Pass query (words such as "carve" or "note") to get only the operations whose name or parameters match, best first, and total, the number of operations there are.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_preview_operation`

What an operation would change, and nothing changed: the map, the data file and the operation log are all left alone. Use this to check a proposal before applying it. Returns what would change, or the refusal.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_apply_operation`

Run one of the editor's operations. Changes the editor (most operations change the open map and write its file; brush_arm only arms a piece) and appends a line to the operation log. Set dry_run to true to see what would change without changing it. Returns the operation's id, which can be cited in a report to the developer, and the log's own record of it. When the operation changes a document and a map is open, the answer's checks field names the edge faults and overlapping placements the change introduced (new, at most 20 of each) with new_total, and each kind's total on the whole map; it is null otherwise. A rules_set whose weights name a prefix no piece in the library starts answers tunes_nothing (in would_change on a preview, and in the summary on an apply), naming the prefix and the pieces it does not tune: the change is applied, because removing a weight list is how an undo restores one, so read that field rather than assuming a weight did something. The operation replaces the values it names rather than adding to them, so it is marked destructive. Take a change back with grimoire_undo_operation and the returned id.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | true |
| `idempotentHint` | false |

### `grimoire_undo_operation`

Take back one change made through grimoire_apply_operation. Pass operation_id, the id that call returned; omit it to take back the newest change that has not been taken back. The editor applies the inverse the change recorded, writes the data file, and appends a new log line naming the line it undoes; the log is never edited. Refuses, and changes nothing, when the change was already undone, when a newer change exists (the answer names it; undo that one first), when the map was changed outside the log since (a hand-edited file, the menu, or another map open; the answer names what differs), or when the change recorded no inverse. Undoing an undo puts the change back, and the change's own id takes it back again. Set dry_run to true to see what the undo would set. Set turn to true to take back the whole result you last presented with grimoire_present, newest change first, in one call — the same amount one Cmd+Z takes back — and the answer says how many changes it took with took_back. turn refuses when nothing has been presented, or when the presentation named no operations. Returns the undo's own operation id and what it set.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | true |
| `idempotentHint` | false |

### `grimoire_state`

What the editor is holding right now: the open map and its bounds, how many pieces it has, what is armed, what is selected, which door and tab are open, and what the editor last said and what has gone wrong. The editor section also names the next undo and redo (undo_next, redo_next) and how many are stacked (undo_depth, redo_depth). The map section names up to 50 pinned placements by id and reason (pinned). pinned_total is the full count; past 50, pass pinned_from (from pinned_next) to read the rest. With --live, game is the running game's verdict on the last reload: null (none), "pending" (it has not answered the latest write) or {ok, message, at_unix_ms, seq, kinds}; kinds has one entry for every file the game read, {kind, file, outcome (applied or refused), field, reason}, so a refusal names its file and field. reloads is the editor's own verdict on the files it draws from (terrain, water_field, volume): {ok, seq, kinds} with the same entries; a refused file keeps what was drawn, and seq counts decisions, one per edit. frame is the editor's own clock: frame_ms (wall time between frames), busy_ms (work done inside one frame) and fps; a high frame_ms with a low busy_ms is the machine, not the editor. The notes section lists the sent and claimed notes (id, holder, lease_until); pass note=<id> for that note's bundle: text, area and margin, nearby pieces, the palette, the camera, a picture recipe and earlier notes. repetition names up to 10 visible repeats (the same piece at one yaw and tip within 6 m; any yaw for a round kind), the one a player notices first first: descriptor, patched, role (clutter or structure), pieces, pairs, score; total counts them all; the radius, the structure kinds, their weight and the round kinds come from the project's repetition.ron, re-read on every call, and a bad file is named in error. relations checks the <map>.relations.ron beside the open map, re-read on every call: each relation (of, kind) with outcome met, unmet or missing, measured (metres, or degrees off for Faces), by (the piece that breaks it) and missing_id; unmet and missing count them; error names a file that does not parse. standards checks the project's standards.ron (beside kits.ron), re-read on every call: breaches (piece, rule, dim, found metres, why below_min, above_max, not_multiple_of or unmeasured, bound), idle, the rules no piece is covered by, and unnested, the pairs of rules whose multiple_of modules do not nest (rules, dims, modules, meet metres where they share a grid line again or null, message); error names a file that does not parse. dead_ends is the kit stress test: every declared face (piece, dir N/E/S/W, face tokens, closest {piece, turn, misses [{at, want, found}]} the piece nearest to meeting it or null, message) that no piece of the kit meets at any quarter turn, up to 20, with total counting them all. stress is the rest of the kit stress test, from the library on every call: ring, the loop the kit closes, four {piece, turn in degrees} north-west, north-east, south-west, south-east; room, the smallest room with a middle, three rows of three {piece, turn} north to south and west to east, the middle at [1][1]; each null when the kit cannot build it; declared counts the pieces with an edge token, and at 0 the nulls say the kit is unlabelled. Returns that summary as JSON, and changes nothing. Call it before a change to know what you are changing, and after one to check that it landed.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_list_pieces`

The library's pieces, a page at a time. Each row carries the piece's id, the mesh it is drawn with (null for a flat footprint marker), its kind, effects and looks, and its labels: who labelled each axis (model, agent or human), the record's model, date and confidence, which report what the record says, not whether anyone has checked it; by_model finds labels no human has confirmed. Filters combine: with_mesh, unlabelled, by_model, confidence (high, medium or low), id_contains. total is the true count after the filters. A page holds 50 rows; past 50, pass pieces_from (from pieces_next) to read the rest, and how_to_narrow names the filters when a filtered page is still capped. Refuses when no project is open, rather than answering an empty list. Returns that page as JSON, and changes nothing.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_capture_still`

A picture of the editor as it is now -- the world and the interface, because the editor draws both into one image -- plus a state summary of the same moment. The picture is returned as an image and written to a file whose path is in the answer. The answer also carries a fingerprint of the picture's bytes: two stills with the same fingerprint are the same picture, so compare fingerprints rather than file paths to tell whether the screen changed. Use this after a change to see what it did, or before one to see what it was like.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | false |
| `idempotentHint` | false |

### `grimoire_snip`

A rectangle of the editor's picture, cut out and returned as an image. rect is [x0, y0, x1, y1] in window pixels, origin at the top left, x1 and y1 exclusive, so the same pixels a still is in. The crop is written to a file whose path is in the answer, with the state of the same moment. It writes one crop file under target/loop and changes no map data: it is not an operation, not logged and not undoable. Refuses, and writes nothing, on a rectangle that is empty, reversed, negative or outside the picture, and says the picture's size. Use it to look closer at one part of a still from grimoire_capture_still.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | false |
| `idempotentHint` | false |

### `grimoire_decide`

Ask a decision model a typed question about the editor's pictures and facts, and get a probability for every allowed answer, with nothing to parse. Two forms. check: a named check such as floating, clipping, outside_area, blank_frame or toast_visible (the editor's own, with the project's assets/grimoire/checks.ron over them, read on every call); it answers a finding with the check's P(yes), its threshold and whether it was found, and takes the editor's current picture itself when it needs view. questions: ad-hoc typed questions by id, each noul (yes or no, P(yes)), choice (named options, each one's probability) or score (levels, a weighted score), with state in words, images (project files, at most four) and facts (JSON). A check that needs a picture or facts it was not given is refused and names what is missing; it never answers from less. Advisory: it changes no map data and a finding never blocks or undoes an operation. The endpoint is one per run, local by default; a Cloudflare endpoint sends pictures off the LAN and is opt-in.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | false |

### `grimoire_list_snips`

The snips the person took in the editor, newest first: each one's name, when it was taken, the map and the active tool, the note the person typed, the rectangle in window and picture pixels, the camera view, the cursor's world position and the placements inside the rectangle. Each entry names its picture file, and the newest picture comes back as an image. It reads files the editor wrote, so it needs no editor running and changes nothing. Returns how many snips there are, how many are shown, the snips still being saved (pending: confirmed in the editor, picture not yet written, so not yet in the snips list) and each .json file in the snips folder that is not a snip record or has no picture file, with the reason.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_list_rules`

The block rules the project states for generating layouts, read from assets/grimoire/rules.ron: for each block, the example map its grammar is learned from, the region descriptors that ask for a block, the cell size and block size in cells, the border piece, no_empty, the weight multipliers, the footprint rules, attempts and seed. Returns the blocks and the path of the file read. A project with no rules.ron answers with no blocks, because an absent file means no rules -- not a broken project. A file that is present but does not parse, or states a version this program does not read or a number it cannot generate from (no attempts, a cell that is not a usable step, a footprint under 2x2, a yaw other than 0 or 180), is refused with its path and the reason, and nothing is written. It parses the file but does not check that the descriptor ids it names exist in the project's library -- the editor's own open does that, so a block naming a missing piece is answered here and refused there. It reads a file, so it needs no editor running and changes nothing.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_capture_sequence`

A sequence of frames of the editor, with an optional operation applied once the first frame is in -- so frame 0 is the state before the action and the later frames are what it did. The frames are written to a directory and their paths are in the answer. The editor takes the frames, so the timing does not depend on this server's round trips. The rate is two to fifteen frames a second. A frame is asked for only once the one before it is written, so a stalled editor delays the frames after it rather than losing them; a frame that does not land within five seconds ends the run with a reason, and the status is done only when every frame is written. The call waits for the run to end, for at most the sequence's length plus five seconds a frame and a margin.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | true |
| `idempotentHint` | false |

### `grimoire_read_oplog`

The editor's operation log, newest last. Every operation appends one line, whether a person or an agent did it. Read it to see what has been done to this project. A refusal is not logged, so a line here is a line about a change that happened. An undo is a new line naming the line it undoes.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `grimoire_frame_view`

Frame the editor's Map camera on a box. target: "map" (the whole map), "selection" (the locked placement; refused when nothing is locked), {"placements": [ids]} (their union), or {"rect": [x0, z0, x1, z1]} (map metres). It only moves the camera: it never changes map data, is not logged or undoable, and is not an operation. Refuses, and moves nothing, on an unknown id, an empty selection or a flat rectangle. Returns what was framed, the focus and the view height in metres. Call grimoire_capture_still afterwards to see the result.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | false |
| `idempotentHint` | true |

## How the two paths converge

Every operation writes the data file, and the editor watches that file. So:

- an **agent** calls `grimoire_apply_operation`, the editor writes the file, and the editor's own state is already the new one;
- a **person** edits the file in a text editor, the watcher notices within a quarter of a second, and the editor re-reads it — **and keeps what it had if the file does not parse**;
- a **person at the keyboard** uses the editor's own controls, which dispatch the same operations.

The measured latency of both paths is in the iteration report.
