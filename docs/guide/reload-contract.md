# The reload contract

This page lists every kind of file the editor writes and says what a running program does when one of them changes on disk. It is the audit that the hot-reload series (issues #198 to #204) builds on.

The list lives in code, in `bevy_grimoire_core::reload::KINDS`, and the table below is rendered from it and from the editor's operations. A test fails when the table is out of date.

## How to read the table

- **kind** is the id an operation names in `Operation::writes`.
- **path** is relative to `<grimoire>` (the project's directory, `assets/grimoire`, the one holding `kits.ron`) or to `<root>` (the game's root, the directory holding `assets/`). `<kit>` is a kit's directory under `<grimoire>`: the authoring kit's library, policy, terrain, water, volume, forest, people, scripts and trees live there. `<name>` and `<kit>` each stand for one word of letters, digits and underscores, and for a per-map kind `<name>` is the map's name. `<file>` is one file name of any characters.
- **parses to** is the Rust type the file is read as.
- **class** is what a change costs the programs this repository ships (the editor, and the game-side `GrimoireLivePlugin`), the dearest of them when they differ.
- **lifetime** is what the file belongs to.
- **written by** names the operations that write it. A kind no operation writes says who does.

### Classes

| class | meaning |
|---|---|
| `Live` | The new content replaces the old in place, or nothing holds the old content because the file is read fresh each time it is used. |
| `Respawn` | What was built from the file (entities, meshes, a world) is dropped and built again. The rest of the program carries on. |
| `Restart` | A running program that holds the kind cannot take a change to it. It keeps the old content until it is restarted. |

### Lifetimes

| lifetime | meaning |
|---|---|
| `global` | One per project, kit, species or crate. It outlives every map, and a change reaches everything that reads it. |
| `per map` | One per map, named after it. It loads with its map, and a change reaches only that map. |

## Two ratchets keep the table honest

- `every_written_kind_has_a_reload_class` (`crates/bevy_grimoire_mapper/tests/reload_contract.rs`). Every operation declares the kinds it writes, and `Operation::writes` has no default, so a new operation cannot skip it. The test fails when an operation names a kind the list does not have. A second test runs an operation and checks that every file it changed is a kind it declares.
- `the_restart_list_only_shrinks` (`crates/bevy_grimoire_core/tests/reload_contract.rs`). Every `Restart` kind is on a checked-in list. A kind joins `Restart` only by editing that list and raising its ceiling, so the debt can be paid down and never grows unseen. Today it is `rigs` and `game_data`.

## A request for a kind that was never loaded

`reload_for(kind, loaded)` is the one policy. A change to a kind the program never loaded is the outcome `Reload::NotLoaded`: it is reported and nothing else happens. It is never an implicit load. A load in the middle of play is a hitch, and a program that did not ask for the file has no state to reload.

## A refusal names its file and its field (#200)

A reload validates before it applies. When a file is refused the previous state stays, and the answer says which file, which field and why. `bevy_grimoire_core::reload_check::check(kind, file, text)` parses a file as its kind with the type's own reader, the one a load uses, so the two cannot disagree. A refusal is a `Refusal { kind, file, field, reason }`: `field` is a path such as `version` or `placements[3].at[1]`, found by reading the file again with `serde_path_to_error` only after it was refused, and it is empty for a file that is not RON or that the type's own validation refused after it parsed (the reason says why). `check` covers 18 of the 33 kinds. The other 15 are on a checked-in list in `crates/bevy_grimoire_core/tests/reload_verdicts.rs` that may shrink and never grow unseen.

The game writes one `Verdict` to `.live/game.ron` for each edit it decides on. Version 2 of the file adds `seq`, which counts the game's decisions so an edit is one number however many frames pass, and `kinds`, one `KindVerdict { kind, file, outcome, field, reason }` for every file the load reads: `kits.ron`, each bound kit's `library.ron` and `project.ron`, `vocab.ron`, `rules.ron` and `compositions.ron` when present, and each map. `outcome` is `applied` or `refused`. The game still reloads the project as one unit, so one refused file keeps the whole previous project, and every other file's entry says `applied` because it is fine by itself. A refusal that is about how files fit together (a map that places a descriptor no library has) goes to the file whose path starts the error, and to a `project` entry when none does.

`grimoire_state.game` carries `seq` and `kinds`, and the editor's journal says `game refused the reload: maps/town.map.ron (placements[3].at[1]): map: 1:47: Expected float`. The tests are `crates/bevy_grimoire_core/tests/reload_verdicts.rs` (three bad files per kind), `crates/bevy_grimoire/tests/live_verdicts.rs` (the game keeps its entities and world, writes one verdict per edit) and `crates/bevy_grimoire_mapper/tests/the_games_per_file_verdicts_reach_grimoire_state.rs`.

The editor decides its own files the same way. The terrain view reads the open map's terrain, water field and carved volume, and keeps the last good parsed value of each in memory: a file that reads replaces its value, a refused one leaves it, so a refused edit leaves the entities drawn before it untouched and a bad file is never read again to redraw (when the origin moves, the drawing is rebuilt from the held values). A map that opens with a file refused has no earlier value and draws without it, and a file that is deleted (an undo) is no longer drawn or refused. Each edit is one decision, kept in `grimoire_state.reloads` (`{ok, seq, kinds}`, the same entries as `game.kinds`) and said once on the status line with the file and field, because the view only reads again when a file's modification time moves. `check` now also reads `water_plan`, `water_field`, `volume` and `data_registry`, with the type's own validation: water that does not fill its shape, an edit with no size, a registry from another version or naming an id twice are refused and say why. The test is `crates/bevy_grimoire_mapper/tests/a_refused_terrain_file_keeps_the_last_good_drawing.rs`.

**A file an operation rewrites is read strictly.** `forest_scatter`, `person_set` and `trigger_set` read their map's file, change one row and write the whole file back. A file that did not parse used to count as no file, so one typo in a hand edit made the next call write a file holding only its own row over everything else. `map_files::read_or_empty` now reads the file with `reload_check::read` and refuses the call, naming the file and the field (`site/people/town.ron (people[0].at): 1:41: Expected a tuple`), and the bytes on disk stay as they were; once the file is fixed the same call applies and keeps the rows that were there. The undo of an earlier call (`put_back`) does not read the file, so it still works. The forest view (a build with `bevy_flora`) decides its file once per edit into `grimoire_state.reloads` as the terrain view does, and keeps the trees drawn. Core cannot read these three kinds, because their types live in the editor, nor `trees` (below), because its type is `bevy_flora`'s, so they stay on core's `UNCHECKED` list and `map_files::READ_HERE` names them; the editor's own ratchet is `STILL_UNCHECKED` in `crates/bevy_grimoire_mapper/tests/a_file_that_does_not_read_is_never_overwritten.rs`, 7 kinds, and the three cases per kind are there.

**A tree file that does not read keeps its trees** (a build with `bevy_flora`). A `.tree.ron` is a species: every tree of it, placed or pooled, is drawn from it. A bad edit used to make the species unknown, so every tree of it vanished from the viewport until the file was fixed. Now the forest view decides each tree file once per edit (it reads it again only when its modification time moves) with the crate's own reader, `reload_check::read::<TreeParams>`, and holds the last good value in memory: a refusal leaves the trees standing exactly as that value drew them (the same entities, nothing redrawn), and is reported in `grimoire_state.reloads` as kind `trees` with the file and the field (`kit/trees/old.tree.ron (undergrowth): 1:20: Expected a boolean`), one entry per file and one number per edit however many frames pass. A tree file that is gone is not a refusal: its trees are not drawn and nothing is reported. `tree_edit` refuses a `set` over a file that does not read the same way, naming the file and the field and leaving the bytes alone (only `preset`, which asks for the file to start again, writes over one, and its undo puts the old text back). Every field of a tree file has a default, so a file cannot be "missing a field"; the third bad file of the three is a field the crate does not know, which ron names. The tests are `crates/bevy_grimoire_mapper/tests/a_refused_tree_file_keeps_the_last_good_tree.rs` and the `trees` case of `a_file_that_does_not_read_is_never_overwritten.rs`.

**Notes keep their last good value, and family settings say what became of an edit** (#200). The signs over the notes and the Notes panel used to read `<map>.notes.ron` themselves and take an empty list when it did not parse, so one bad edit made every sign and row vanish until the file was fixed. One view (`notes_view::NotesView`, synced by `sync_notes_view`) now looks at the file every frame by its size and modification time (and once a second regardless, because two writes inside one coarse timestamp tick look alike), holds the last good `Notes` in memory and decides each edit once, keeping the text it last read so the same bytes are never decided twice: a file that reads replaces them, a refused one (`Notes::from_ron`: not RON, the wrong type, a field missing, a version this build does not read, an id twice) leaves them and is reported as kind `notes` with the file and the field (`maps/yard.notes.ron (notes): ...`) in `grimoire_state.reloads` and on the status line, and a deleted file empties them and clears its verdict. The family host's `reload_settings` reports kind `family` the same way, one decision per poll that saw a change, naming the file under the game's root (`family/bevy_elements.ron`) because that is where a `family` kind's pattern starts: a file that is RON replaces the crate's settings and is `applied`, one that is not is `refused` with why and the last good settings stay, a deleted one is no longer listed, and the files read when the editor opens a project are decided once at the start, one that was already not valid RON included (it has no earlier value, so its crate's defaults apply). `FamilyWatch` reports a change from the settings in force, so a refused file put back to exactly those is no change to it, and a file that never read and is then deleted was never in force to be removed; the host compares each refused file with the disk twice a second, so the first is `applied` again and the second is forgotten, and the same bad bytes are decided once however often the watch says so. What the crate's own type makes of settings that are valid RON but the wrong shape is not decided here, because the type lives in the crate. The tests are `crates/bevy_grimoire_mapper/tests/a_refused_notes_file_keeps_the_last_good_notes.rs` and `family_settings_verdicts.rs`.

**A kind the program holds from its start says `needs_restart`** (#200). The animation tab reads `rigs.ron` when it loads (the first entry to the tab, and again after a door change resets the bench) and holds what it read (the registry classes the kind `Restart`), so an edit to the file on disk used to do nothing and say nothing, and a broken edit looked the same as a good one. `anim_watch::sync_rigs_reload` now looks at the file every frame by its size and modification time (and once a second regardless), compares it with the text the tab holds and decides each distinct edit once into `grimoire_state.reloads` as kind `rigs`: `needs_restart` when the file reads (the third outcome beside `applied` and `refused`: the edit is on disk and not in use, the tab keeps what it holds, and `reason` says to change door and come back, or restart the editor), `refused` with the file and the field when it does not read (`rigs.ron (version): rigs.ron is not valid: ...`, with the parser's own position and message after it). A file that is gone is `needs_restart` too, and an edit put back as it was clears the verdict, because the file and the tab agree again; so does a door change, which drops what the tab held, and the next load reads the file as it is. A file that did not read when the tab loaded leaves the tab with no rigs: it is `refused` as soon as it is looked at (the status line says `no rigs are loaded from it`), and a fix is `needs_restart` (the tab loaded no rigs and reads it again only when it loads afresh). The tab's own writes (adopting measured values, an undo) update the held text with the file, so they say nothing. `ok` is false while any file is not `applied`. The game never writes `needs_restart`: it reloads its project as one unit and holds no `Restart` kind. The test is `crates/bevy_grimoire_mapper/tests/a_rigs_edit_says_what_became_of_it.rs`, and `crates/bevy_grimoire_core/tests/a_restart_verdict_says_so.rs` pins the outcome's word and its round trip through `.live/game.ron`.

**Data an earlier release wrote keeps reading** (#200, build step 5). A settings type may gain a field only if the field has a default, and may lose one only if no file still carries it (a removed field is refused for a type that denies unknown fields, which most do; Kleppmann, on schema evolution: a new reader reads old data only if the fields it added default). An edit that breaks either refuses every project already on disk, and no test noticed, because each one reads a value the current type just wrote. `crates/bevy_grimoire_core/tests/old_data/` now freezes one file of every kind `reload_check::check` reads, as a release wrote it: `core-0.1.0/` holds the project files exactly as `bevy_emerge_core` 0.1.0, the first release, shipped them (kits, vocab, two libraries, two policies, compositions, rigs), and `core-0.3.0/` what `bevy_grimoire_core` 0.3.0 writes for the kinds the first release had no sample of, each collection holding one element so the element types are read too. `tests/old_data.rs` reads each with the type's own reader and refuses the edit by naming the kind, the file, the field and the release (`standards (standards.ron) written by bevy_grimoire_core 0.3.0 no longer reads, at field review_m`). With a required `review_m` added to `Standards`, the three-bad-files tests all still pass and this one fails. A frozen file is never edited: a type that has to change shape bumps its version, migrates the old one and keeps the old file reading, and the new version's file is added beside it. A floor in the test stops a frozen file being dropped to make a type pass, and a second test keeps every kind `check` reads covered. The 11 kinds `check` cannot read (the editor reads four of them itself) have no frozen data yet.

**Project checks keep their last good value** (#200). `Checks::for_project` read `assets/grimoire/checks.ron` fresh on every run, so one bad edit stopped every after-edit check: the journal said "after-edit checks not run" with the parser's position and no field, and the second reader (the run that follows a screenshot) dropped the error altogether. `checks_view::ChecksView`, synced by `sync_checks_view` (registered by `AfterEditPlugin`, so it looks in every door: the checks belong to the project, not to the open map), now looks at the file every frame by its size and modification time (and once a second regardless), holds the editor's checks with the project's over them as of the last read that was good, and decides each edit once into `grimoire_state.reloads` as kind `checks`: `applied`, or `refused` with the file and the field (`checks.ron (checks[0].question): 1:35-1:36: Expected string`) and one line on the status line. A file that does not parse names its field (read again with `serde_path_to_error`, as for every kind; for a file cut off, where reading stopped); one that parses and breaks a rule (two checks of one name, a threshold outside 0..=1) has no one field and says which rule in its reason, and so does a file that is there and cannot be read (not UTF-8, no permission), which is not the same as a file that is gone. `after_edit` asks the held checks (`checks_view::checks_for`), so a refused edit leaves the checks running as the last good file defined them; a file that was broken from the first look has no earlier state, so the reader's own error stands and the verdict names the field. A file that is gone is the editor's own checks alone and ends its refusal. The MCP `decide` tool is another process and still reads the file fresh, so it names the position and not the field. The tests are `crates/bevy_grimoire_mapper/tests/a_refused_checks_file_keeps_the_last_good_checks.rs` (five ways to break the file, one verdict per edit, the checks asked stay the last good ones, a fix replaces them, a removed file clears the verdict, a file broken at open or unreadable, every door).

**The operation log names a damaged line** (#200). `assets/grimoire/oplog.jsonl` is append-only text that a person can edit and a crash can cut short, and the readers that walk it (the steps feed, `grimoire/oplog_read`, the after-edit queue) skip a line that is not an entry, so a damaged line cost the author what it recorded and said nothing: the journal counted "line(s) of the log could not be read" with no line and no field, and the undo walk refused at one without naming the field. Nothing holds the log, so there is no last good value to keep; what the editor owes is the verdict. `oplog_view::sync_oplog_view` (registered by `AfterEditPlugin`, so it looks in every door) reads the file when its size or modification time moves (and once a second regardless, a read of text it already parsed costing a hash) and decides what it found into `grimoire_state.reloads` as kind `oplog`: `applied` while every line reads as an entry, or `refused` with the file, the line and the field of the first line that does not (`oplog.jsonl (line 3.seq): invalid type: string "one", expected u64 (column 14); 1 more line does not read`) and one line on the status line. The field is `line N.<path>` as `reload_check::read_lines` reads it (N counted from 1 as an editor shows it, a blank line counted), `line N.op` for a missing field, `line N` for text that is not JSON or trailing text after an entry (two entries glued by a write cut short), and a line cut off names where reading stopped. The editor appends a line for every operation, and a log that still reads is not news, so a look decides only when what it found differs from the look before: an append to a log that reads is no verdict, a damaged line is one, a repaired one is one, and a log that is gone clears it. A log that is there and cannot be read at all (not UTF-8, a directory) is refused with no line. The undo walk reads the log with the same reader, so an undo past a damaged line refuses naming the file, the line and the field, and writes nothing: the newest change in effect may be the line that does not read, so it never guesses around it. The readers that skip, skip as before.

**A game's data files say whether they still read** (#200). `<grimoire>/<kit>/data.ron` registers the tuning files a game owns and bounds the leaves the editor tunes; the Data panel and `data_set` read them, and nothing here applies them to a running game (the registry classes them `Restart`). A hand edit that stopped reading therefore cost the panel its rows with no word (it still lists no rows for such a file), and `data_set` refused a file that did not scan without naming it. `data_files::read` is now the one reader `data_set` and the editor's look use: it refuses a file cut off at the leaf where reading stopped (`mob.name`) and one that is not RON with no leaf, and `data_files::check` adds what the file's type would be, since the file's own type is the game's: every leaf the registry bounds must be there (a missing one is named with the nearest leaves), a number (a word is named by its path) and inside its bounds. `data_view::sync_data_view` (registered by `AfterEditPlugin`) looks at the registry and each file it lists when a size or modification time moves, and once a second regardless, and decides into `grimoire_state.reloads` kind `game_data` per file and kind `data_registry`. A file that does not read is `refused` with the file, the leaf and why (or with no leaf for a file that is registered and not there). A file that reads again is judged against the text the editor first saw reading, which is what a game started with as far as it can tell: the same text is `applied` (a net-zero edit leaves nothing waiting), any other is `needs_restart`, and the reason says a running game uses it only if it re-reads its data, and otherwise at its next start. A file seen reading for the first time is a baseline, not an edit, so opening a project says nothing; a file first seen refused has no baseline, so what mends it is `needs_restart`. The baseline is kept while a refused registry takes the file out of the verdicts, so an edit made meanwhile is still said when the registry reads again. The registry itself is `applied` when an edit leaves it reading and `refused` with its field (`files[0].path`) when it does not. One edit is one `seq`, and frames without an edit decide nothing. `data_set` over a file that does not scan refuses with the file and the leaf and leaves its bytes as they were.

Still to do in #200: a reader that names the file and the field for the 4 kinds nothing reads yet (`reference_images`, `family`, `destructible_marks`, `destructible_bake`).

## What the audit found

These are the facts the later issues in the series start from.

- **The game's watcher sees every `.ron` under its directory** (`GrimoireLivePlugin`, the extension set `{ron}`) and runs the whole project load. It diffs placements, the library and masks. A change to a kind it does not read (notes, plans, references, forests) fires a reload that changes nothing, and a broken file of such a kind does not turn the verdict false, because nothing parses it. The class column names what each kind costs, not what the watcher notices.
- **The editor watches by name** (`watch.rs`): `kits.ron`, `vocab.ron`, `compositions.ron`, `rules.ron`, `standards.ron`, `repetition.ron`, each kit's `library.ron` and `project.ron`, and the open map. Terrain, water, volume, forest and tree files are polled by modification time in the views that draw them, and family settings by the family host every 0.1 s. Notes are looked at every frame by size and modification time.
- **A file that does not read keeps the last good state in the project watcher, the game, the terrain view, the forest view, the tree files the forest draws from, the notes view and the family settings** (the editor says "kept what it had"). The editor's views and watchers report each edit in `grimoire_state.reloads`; the ones still outside it are listed under "Still to do".
- **Every write of a project file is atomic since #199.** The audit found `family`, `game_data`, `people`, `forest`, `scripts`, `terrain`, `trees`, `volume`, `water_plan`, `water_field`, `destructible_marks`, `destructible_bake`, `reference_images`, and `kits` and `vocab` at project creation written in place, so a reader could see half a file. All of them now go through `bevy_grimoire_core::atomic_file`: a uniquely named hidden temp file (`.<name>.<pid>-<n>.tmp`, never a `.ron` and skipped by the watcher) beside the target, flushed, renamed over it, then the directory flushed. A reader thread parses a map while it is replaced ten thousand times without the flushes and three hundred times with them, a writer process is killed at forty random points, four threads write one path, and `tests/atomic_writes_only.rs` fails on a new plain `fs::write`, `File::create`, `fs::copy` or `OpenOptions` in the non-test source of `bevy_grimoire_core` and `bevy_grimoire_mapper` (a write through another API is not seen by it). What is promised is no torn read and no half-written file after the writer dies; durability against power loss is not, because a test cannot show it. Caches (thumbnails, the animation bench cache) use `write_cache`, the same rename without the flushes.
- **`game_data` is a `Restart` kind** because `data_set` writes files the game owns and this repository ships no reader for them. Whether a game re-reads them is the game's. #202 moves behaviour into data and scripts so the list shrinks.

## What is not a kind

These are written but are not project data, so they have no class. None is read back as project data.

- `<grimoire>/.live/game.ron`, the game's verdict on its latest reload. The game writes it, and the watcher skips every name that starts with a dot so it cannot trigger the reload it reports.
- `slop/llm/vocab_proposals.ron`, a VLM's label proposals, `target/grimoire_thumbs/`, `target/anim_bench_cache.ron` and `target/loop/captures/snips/`: caches and captures.
