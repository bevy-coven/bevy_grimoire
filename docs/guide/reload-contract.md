# The reload contract

This page lists every kind of file the editor writes and says what a running program does when one of them changes on disk. It is the audit that the hot-reload series (issues #198 to #204) builds on.

The list lives in code, in `bevy_grimoire_core::reload::KINDS`, and the table below is rendered from it and from the editor's operations. A test fails when the table is out of date.

## How to read the table

- **kind** is the id an operation names in `Operation::writes`.
- **path** is relative to `<grimoire>` (the project's directory, `assets/grimoire`, the one holding `kits.ron`) or to `<root>` (the game's root, the directory holding `assets/`). `<kit>` is a kit's directory under `<grimoire>`: the authoring kit's library, policy, terrain, water, volume, forest, people, scripts and trees live there. `<name>` and `<kit>` each stand for one word of letters, digits and underscores, and for a per-map kind `<name>` is the map's name. `<file>` is one file name of any characters.
- **parses to** is the Rust type the file is read as.
- **class** is what a change costs the programs this repository ships (the editor, and the game-side `GrimoireLivePlugin`), the dearest of them when they differ.
- **lifetime** is what the file belongs to.
- **written by** names the operations that write it. A kind no operation writes says who does.

### Classes

| class | meaning |
|---|---|
| `Live` | The new content replaces the old in place, or nothing holds the old content because the file is read fresh each time it is used. |
| `Respawn` | What was built from the file (entities, meshes, a world) is dropped and built again. The rest of the program carries on. |
| `Restart` | A running program that holds the kind cannot take a change to it. It keeps the old content until it is restarted. |

### Lifetimes

| lifetime | meaning |
|---|---|
| `global` | One per project, kit, species or crate. It outlives every map, and a change reaches everything that reads it. |
| `per map` | One per map, named after it. It loads with its map, and a change reaches only that map. |

## Two ratchets keep the table honest

- `every_written_kind_has_a_reload_class` (`crates/bevy_grimoire_mapper/tests/reload_contract.rs`). Every operation declares the kinds it writes, and `Operation::writes` has no default, so a new operation cannot skip it. The test fails when an operation names a kind the list does not have. A second test runs an operation and checks that every file it changed is a kind it declares.
- `the_restart_list_only_shrinks` (`crates/bevy_grimoire_core/tests/reload_contract.rs`). Every `Restart` kind is on a checked-in list. A kind joins `Restart` only by editing that list and raising its ceiling, so the debt can be paid down and never grows unseen. Today it is `rigs` and `game_data`.

## What will always need a rebuild (#202)

The restart list above is debt: a kind with a file that no running program re-reads yet. A different thing needs no file at all and is not on it: a setting that is a Rust type, and that a file cannot hold. The list lives in code, in `bevy_grimoire_core::reload::REBUILD`, with the reason for each entry, and the table below is rendered from it. `a_setting_is_never_both_a_file_kind_and_a_rebuild` fails if an entry gains a file kind and stays here, so an entry leaves the list in the commit that gives it a reload path.

## Every format carries a version (#202)

A format with no version number cannot change shape without breaking the projects already on disk: a reader cannot tell an old file from a damaged one, and a file from a newer build is read as if it were this one's. `crates/bevy_grimoire_core/tests/every_format_carries_a_version.rs` puts every kind of the table in exactly one of four places, and a new kind fails it until it says which.

- **Versioned** (24 kinds: `kits`, `vocab`, `library`, `policy`, `rules`, `compositions`, `standards`, `repetition`, `rigs`, `map`, `notes`, `plan`, `references`, `relations`, `terrain`, `water_plan`, `water_field`, `volume`, `data_registry`, `family_list`, `agent`, `play`, `destructible_marks`, `destructible_bake`). A file one version ahead of what the build reads is refused, and the refusal names the version the build reads, so an author knows the project came from a newer release and is not damaged. A file from before the first version (version 0) is read or refused naming the version. `rules` and `destructible_marks` read a newer file as their own until #202 slice 1: the reload verdict said `applied` for a `rules.ron` that the project open refuses, and `destructible_set` would have written a newer marks file back at the older version. Both now refuse it, the reload check and the two operations that read the marks (`destructible_set` and `destructible_hit`), and leave the bytes as they are. A cache is the one exception: a `destructible_bake` of another version is stale, not damaged, and is baked again.
- **Gained a version in slice 2** (6 of those kinds: `vocab`, `repetition`, `terrain`, `water_plan`, `water_field`, `volume`). Each type has a root `version: u32` declared with `bevy_grimoire_core::format_version`: `default = first` makes a file from before the version the first one, so no project on disk is rewritten, and `deserialize_with = read` makes the type itself refuse another number (`version 2 is not the 1 this build reads`). The refusal is in the type and not in its `parse` because an editor operation reads with a plain `ron::from_str` and writes the whole file back: a refusal only `parse` raised would protect the reload check and leave `terrain_stroke`, `water_place` and `volume_edit` writing a newer file at this build's version. What the type writes carries `version: 1`. `crates/bevy_grimoire_core/tests/a_format_that_gains_a_version_reads_the_files_it_did_not_have_one_in.rs` proves both for a plain reader and `reload_check::read`, and `crates/bevy_grimoire_mapper/tests/a_terrain_water_or_volume_file_of_another_version_is_refused.rs` proves the three operations leave the bytes as they are. Adding the field is a semver-breaking change to six public structs, so `bevy_grimoire_core` goes to 0.5.0.
- **Versioned above this crate** (4 kinds: `forest`, `people`, `scripts`, `checks`; slice 3). The types live in the editor (`ops_forest::Forest`, `ops_people::People`, `ops_scripts::Scripts`, `FOREST_VERSION`, `PEOPLE_VERSION`, `SCRIPTS_VERSION`) and in the decision crate (`Checks`, `CHECKS_VERSION`), so core cannot parse a sample. Each has the same root `version: u32` with `default = first` and a refusal in the type's own deserialiser (the decision crate keeps its own two small functions: it has no dependency on core), so `forest_scatter`, `person_set` and `trigger_set`, which read with `reload_check::read` and write the whole file back, the forest view, the checks view and `Checks::for_project` all refuse a file of another version, naming the field `version` and the version the build reads, and a file with no `version` is the first and is written back with one. The entry in the audit names the test that proves it (`crates/bevy_grimoire_mapper/tests/a_forest_people_or_scripts_file_of_another_version_is_refused.rs`, `crates/bevy_grimoire_decide/tests/a_checks_file_of_another_version_is_refused.rs`), and `a_kind_versioned_above_this_crate_names_a_proof_that_is_there` fails when that file is gone or never names the kind. The editor writes `version: 1` into these files from now on, so a game that reads `forest/<map>.ron`, `people/<map>.ron` or `scripts/<map>.ron` with a type of its own that denies unknown fields must accept a `version` field (no game code in this repository and none in Sanctuary reads them today, checked by search on 2026-11-01). The decision crate and the editor are not published, so no crate was released for this slice.
- **Versioned above this crate, the log (slice 4)** (1 kind: `oplog`). The log is a file of lines, one JSON entry each, so its version is a field of every line: `ops::Entry` has a root `version: u32` (`OPLOG_VERSION`, 1) declared like the others, `default = first` for a line written before it existed (so no log on disk is rewritten) and a refusal in the entry's own deserialiser. Every new line is written at this build's version and an append never rewrites a line, so a log may hold lines of more than one build. What a reader does with a line of another version is what it does with any line that does not read as an entry: the reload verdict (`grimoire_state.reloads`, kind `oplog`) is `refused` naming `line N.version` and `version 2 is not the 1 this build reads`, an undo (`ops::undo_target`) refuses naming the same line and changes nothing, and the readers that parse each line as an entry and skip one that does not read (`ops::read_entries`, the steps feed, the after-edit queue) skip it, so the lines around it still read. `grimoire/oplog_read` returns each line as the JSON it is and refuses nothing. The proof is `crates/bevy_grimoire_mapper/tests/an_oplog_line_of_another_version_is_refused.rs`. Still lenient, as they were for a damaged line (filed as #207): a note's undo (`note_undo_work`) and the pieces credited to an agent (`agent_made_ids`) read the log with `read_entries`, so a line they skip is a change they do not see.
- **Unversioned** (0 kinds). The debt is paid: `the_unversioned_list_only_shrinks` holds the list at zero, so a new kind has to be versioned, versioned above, or owned elsewhere before the audit passes. A kind that cannot be versioned yet is added to the list in the commit that adds it, and the ratchet is raised there, where a reviewer sees it.
- **Owned elsewhere** (4 kinds: `reference_images`, `game_data`, `family`, `trees`). The file's format is somebody else's to version: an image's own header, a game's own RON, a family crate's own settings. The entry in the test says whose.

## A request for a kind that was never loaded

`reload_for(kind, loaded)` is the one policy. A change to a kind the program never loaded is the outcome `Reload::NotLoaded`: it is reported and nothing else happens. It is never an implicit load. A load in the middle of play is a hitch, and a program that did not ask for the file has no state to reload.

## A refusal names its file and its field (#200)

A reload validates before it applies. When a file is refused the previous state stays, and the answer says which file, which field and why. `bevy_grimoire_core::reload_check::check(kind, file, text)` parses a file as its kind with the type's own reader, the one a load uses, so the two cannot disagree. A refusal is a `Refusal { kind, file, field, reason }`: `field` is a path such as `version` or `placements[3].at[1]`, found by reading the file again with `serde_path_to_error` only after it was refused, and it is empty for a file that is not RON or that the type's own validation refused after it parsed (the reason says why). `check` covers 24 of the 33 kinds. The other 9 are on a checked-in list in `crates/bevy_grimoire_core/tests/reload_verdicts.rs` that may shrink and never grow unseen.

The editor's layer reads all 9 since #200 slice 12 (`forest`, `people`, `scripts` and `trees` through `map_files::READ_HERE`; `checks`, `oplog`, `game_data`, `reference_images` and `family` through `map_files::WATCHED_HERE`), so every kind in the registry names its file and its field when it does not read, and the mapper's ratchet of kinds nothing reads (`STILL_UNCHECKED`) is empty.

The game writes one `Verdict` to `.live/game.ron` for each edit it decides on. Version 2 of the file adds `seq`, which counts the game's decisions so an edit is one number however many frames pass, and `kinds`, one `KindVerdict { kind, file, outcome, field, reason }` for every file the load reads: `kits.ron`, each bound kit's `library.ron` and `project.ron`, `vocab.ron`, `rules.ron` and `compositions.ron` when present, and each map. `outcome` is `applied` or `refused`. The game still reloads the project as one unit, so one refused file keeps the whole previous project, and every other file's entry says `applied` because it is fine by itself. A refusal that is about how files fit together (a map that places a descriptor no library has) goes to the file whose path starts the error, and to a `project` entry when none does.

`grimoire_state.game` carries `seq` and `kinds`, and the editor's journal says `game refused the reload: maps/town.map.ron (placements[3].at[1]): map: 1:47: Expected float`. The tests are `crates/bevy_grimoire_core/tests/reload_verdicts.rs` (three bad files per kind), `crates/bevy_grimoire/tests/live_verdicts.rs` (the game keeps its entities and world, writes one verdict per edit) and `crates/bevy_grimoire_mapper/tests/the_games_per_file_verdicts_reach_grimoire_state.rs`.

The editor decides its own files the same way. The terrain view reads the open map's terrain, water field and carved volume, and keeps the last good parsed value of each in memory: a file that reads replaces its value, a refused one leaves it, so a refused edit leaves the entities drawn before it untouched and a bad file is never read again to redraw (when the origin moves, the drawing is rebuilt from the held values). A map that opens with a file refused has no earlier value and draws without it, and a file that is deleted (an undo) is no longer drawn or refused. Each edit is one decision, kept in `grimoire_state.reloads` (`{ok, seq, kinds}`, the same entries as `game.kinds`) and said once on the status line with the file and field, because the view only reads again when a file's modification time moves. `check` now also reads `water_plan`, `water_field`, `volume` and `data_registry`, with the type's own validation: water that does not fill its shape, an edit with no size, a registry from another version or naming an id twice are refused and say why. The test is `crates/bevy_grimoire_mapper/tests/a_refused_terrain_file_keeps_the_last_good_drawing.rs`.

**A file an operation rewrites is read strictly.** `forest_scatter`, `person_set` and `trigger_set` read their map's file, change one row and write the whole file back. A file that did not parse used to count as no file, so one typo in a hand edit made the next call write a file holding only its own row over everything else. `map_files::read_or_empty` now reads the file with `reload_check::read` and refuses the call, naming the file and the field (`site/people/town.ron (people[0].at): 1:41: Expected a tuple`), and the bytes on disk stay as they were; once the file is fixed the same call applies and keeps the rows that were there. The undo of an earlier call (`put_back`) does not read the file, so it still works. The forest view (a build with `bevy_flora`) decides its file once per edit into `grimoire_state.reloads` as the terrain view does, and keeps the trees drawn. Core cannot read these three kinds, because their types live in the editor, nor `trees` (below), because its type is `bevy_flora`'s, so they stay on core's `UNCHECKED` list and `map_files::READ_HERE` names them; the editor's own ratchet is `STILL_UNCHECKED` in `crates/bevy_grimoire_mapper/tests/a_file_that_does_not_read_is_never_overwritten.rs`, 7 kinds, and the three cases per kind are there.

**A tree file that does not read keeps its trees** (a build with `bevy_flora`). A `.tree.ron` is a species: every tree of it, placed or pooled, is drawn from it. A bad edit used to make the species unknown, so every tree of it vanished from the viewport until the file was fixed. Now the forest view decides each tree file once per edit (it reads it again only when its modification time moves) with the crate's own reader, `reload_check::read::<TreeParams>`, and holds the last good value in memory: a refusal leaves the trees standing exactly as that value drew them (the same entities, nothing redrawn), and is reported in `grimoire_state.reloads` as kind `trees` with the file and the field (`kit/trees/old.tree.ron (undergrowth): 1:20: Expected a boolean`), one entry per file and one number per edit however many frames pass. A tree file that is gone is not a refusal: its trees are not drawn and nothing is reported. `tree_edit` refuses a `set` over a file that does not read the same way, naming the file and the field and leaving the bytes alone (only `preset`, which asks for the file to start again, writes over one, and its undo puts the old text back). Every field of a tree file has a default, so a file cannot be "missing a field"; the third bad file of the three is a field the crate does not know, which ron names. The tests are `crates/bevy_grimoire_mapper/tests/a_refused_tree_file_keeps_the_last_good_tree.rs` and the `trees` case of `a_file_that_does_not_read_is_never_overwritten.rs`.

**Notes keep their last good value, and family settings say what became of an edit** (#200). The signs over the notes and the Notes panel used to read `<map>.notes.ron` themselves and take an empty list when it did not parse, so one bad edit made every sign and row vanish until the file was fixed. One view (`notes_view::NotesView`, synced by `sync_notes_view`) now looks at the file every frame by its size and modification time (and once a second regardless, because two writes inside one coarse timestamp tick look alike), holds the last good `Notes` in memory and decides each edit once, keeping the text it last read so the same bytes are never decided twice: a file that reads replaces them, a refused one (`Notes::from_ron`: not RON, the wrong type, a field missing, a version this build does not read, an id twice) leaves them and is reported as kind `notes` with the file and the field (`maps/yard.notes.ron (notes): ...`) in `grimoire_state.reloads` and on the status line, and a deleted file empties them and clears its verdict. The family host's `reload_settings` reports kind `family` the same way, one decision per poll that saw a change, naming the file under the game's root (`family/bevy_elements.ron`) because that is where a `family` kind's pattern starts: a file that is RON replaces the crate's settings and is `applied`, one that is not is `refused` with why and the last good settings stay, a deleted one is no longer listed, and the files read when the editor opens a project are decided once at the start, one that was already not valid RON included (it has no earlier value, so its crate's defaults apply). `FamilyWatch` reports a change from the settings in force, so a refused file put back to exactly those is no change to it, and a file that never read and is then deleted was never in force to be removed; the host compares each refused file with the disk twice a second, so the first is `applied` again and the second is forgotten, and the same bad bytes are decided once however often the watch says so. What the crate's own type makes of settings that are valid RON but the wrong shape is not decided here, because the type lives in the crate. The tests are `crates/bevy_grimoire_mapper/tests/a_refused_notes_file_keeps_the_last_good_notes.rs` and `family_settings_verdicts.rs`.

**A kind the program holds from its start says `needs_restart`** (#200). The animation tab reads `rigs.ron` when it loads (the first entry to the tab, and again after a door change resets the bench) and holds what it read (the registry classes the kind `Restart`), so an edit to the file on disk used to do nothing and say nothing, and a broken edit looked the same as a good one. `anim_watch::sync_rigs_reload` now looks at the file every frame by its size and modification time (and once a second regardless), compares it with the text the tab holds and decides each distinct edit once into `grimoire_state.reloads` as kind `rigs`: `needs_restart` when the file reads (the third outcome beside `applied` and `refused`: the edit is on disk and not in use, the tab keeps what it holds, and `reason` says to change door and come back, or restart the editor), `refused` with the file and the field when it does not read (`rigs.ron (version): rigs.ron is not valid: ...`, with the parser's own position and message after it). A file that is gone is `needs_restart` too, and an edit put back as it was clears the verdict, because the file and the tab agree again; so does a door change, which drops what the tab held, and the next load reads the file as it is. A file that did not read when the tab loaded leaves the tab with no rigs: it is `refused` as soon as it is looked at (the status line says `no rigs are loaded from it`), and a fix is `needs_restart` (the tab loaded no rigs and reads it again only when it loads afresh). The tab's own writes (adopting measured values, an undo) update the held text with the file, so they say nothing. `ok` is false while any file is not `applied`. The game never writes `needs_restart`: it reloads its project as one unit and holds no `Restart` kind. The test is `crates/bevy_grimoire_mapper/tests/a_rigs_edit_says_what_became_of_it.rs`, and `crates/bevy_grimoire_core/tests/a_restart_verdict_says_so.rs` pins the outcome's word and its round trip through `.live/game.ron`.

**Data an earlier release wrote keeps reading** (#200, build step 5). A settings type may gain a field only if the field has a default, and may lose one only if no file still carries it (a removed field is refused for a type that denies unknown fields, which most do; Kleppmann, on schema evolution: a new reader reads old data only if the fields it added default). An edit that breaks either refuses every project already on disk, and no test noticed, because each one reads a value the current type just wrote. `crates/bevy_grimoire_core/tests/old_data/` now freezes one file of every kind `reload_check::check` reads, as a release wrote it: `core-0.1.0/` holds the project files exactly as `bevy_emerge_core` 0.1.0, the first release, shipped them (kits, vocab, two libraries, two policies, compositions, rigs), and `core-0.3.0/` what `bevy_grimoire_core` 0.3.0 writes for the kinds the first release had no sample of, each collection holding one element so the element types are read too. `tests/old_data.rs` reads each with the type's own reader and refuses the edit by naming the kind, the file, the field and the release (`standards (standards.ron) written by bevy_grimoire_core 0.3.0 no longer reads, at field review_m`). With a required `review_m` added to `Standards`, the three-bad-files tests all still pass and this one fails. A frozen file is never edited: a type that has to change shape bumps its version, migrates the old one and keeps the old file reading, and the new version's file is added beside it. A floor in the test stops a frozen file being dropped to make a type pass, and a second test keeps every kind `check` reads covered. The 11 kinds `check` cannot read (the editor reads four of them itself) have no frozen data yet.

**Project checks keep their last good value** (#200). `Checks::for_project` read `assets/grimoire/checks.ron` fresh on every run, so one bad edit stopped every after-edit check: the journal said "after-edit checks not run" with the parser's position and no field, and the second reader (the run that follows a screenshot) dropped the error altogether. `checks_view::ChecksView`, synced by `sync_checks_view` (registered by `AfterEditPlugin`, so it looks in every door: the checks belong to the project, not to the open map), now looks at the file every frame by its size and modification time (and once a second regardless), holds the editor's checks with the project's over them as of the last read that was good, and decides each edit once into `grimoire_state.reloads` as kind `checks`: `applied`, or `refused` with the file and the field (`checks.ron (checks[0].question): 1:35-1:36: Expected string`) and one line on the status line. A file that does not parse names its field (read again with `serde_path_to_error`, as for every kind; for a file cut off, where reading stopped); one that parses and breaks a rule (two checks of one name, a threshold outside 0..=1) has no one field and says which rule in its reason, and so does a file that is there and cannot be read (not UTF-8, no permission), which is not the same as a file that is gone. `after_edit` asks the held checks (`checks_view::checks_for`), so a refused edit leaves the checks running as the last good file defined them; a file that was broken from the first look has no earlier state, so the reader's own error stands and the verdict names the field. A file that is gone is the editor's own checks alone and ends its refusal. The MCP `decide` tool is another process and still reads the file fresh, so it names the position and not the field. The tests are `crates/bevy_grimoire_mapper/tests/a_refused_checks_file_keeps_the_last_good_checks.rs` (five ways to break the file, one verdict per edit, the checks asked stay the last good ones, a fix replaces them, a removed file clears the verdict, a file broken at open or unreadable, every door).

**The operation log names a damaged line** (#200). `assets/grimoire/oplog.jsonl` is append-only text that a person can edit and a crash can cut short, and the readers that walk it (the steps feed, `grimoire/oplog_read`, the after-edit queue) skip a line that is not an entry, so a damaged line cost the author what it recorded and said nothing: the journal counted "line(s) of the log could not be read" with no line and no field, and the undo walk refused at one without naming the field. Nothing holds the log, so there is no last good value to keep; what the editor owes is the verdict. `oplog_view::sync_oplog_view` (registered by `AfterEditPlugin`, so it looks in every door) reads the file when its size or modification time moves (and once a second regardless, a read of text it already parsed costing a hash) and decides what it found into `grimoire_state.reloads` as kind `oplog`: `applied` while every line reads as an entry, or `refused` with the file, the line and the field of the first line that does not (`oplog.jsonl (line 3.seq): invalid type: string "one", expected u64 (column 14); 1 more line does not read`) and one line on the status line. The field is `line N.<path>` as `reload_check::read_lines` reads it (N counted from 1 as an editor shows it, a blank line counted), `line N.op` for a missing field, `line N` for text that is not JSON or trailing text after an entry (two entries glued by a write cut short), and a line cut off names where reading stopped. The editor appends a line for every operation, and a log that still reads is not news, so a look decides only when what it found differs from the look before: an append to a log that reads is no verdict, a damaged line is one, a repaired one is one, and a log that is gone clears it. A log that is there and cannot be read at all (not UTF-8, a directory) is refused with no line. The undo walk reads the log with the same reader, so an undo past a damaged line refuses naming the file, the line and the field, and writes nothing: the newest change in effect may be the line that does not read, so it never guesses around it. The readers that skip, skip as before.

**A game's data files say whether they still read** (#200). `<grimoire>/<kit>/data.ron` registers the tuning files a game owns and bounds the leaves the editor tunes; the Data panel and `data_set` read them, and nothing here applies them to a running game (the registry classes them `Restart`). A hand edit that stopped reading therefore cost the panel its rows with no word (it still lists no rows for such a file), and `data_set` refused a file that did not scan without naming it. `data_files::read` is now the one reader `data_set` and the editor's look use: it refuses a file cut off at the leaf where reading stopped (`mob.name`) and one that is not RON with no leaf, and `data_files::check` adds what the file's type would be, since the file's own type is the game's: every leaf the registry bounds must be there (a missing one is named with the nearest leaves), a number (a word is named by its path) and inside its bounds. `data_view::sync_data_view` (registered by `AfterEditPlugin`) looks at the registry and each file it lists when a size or modification time moves, and once a second regardless, and decides into `grimoire_state.reloads` kind `game_data` per file and kind `data_registry`. A file that does not read is `refused` with the file, the leaf and why (or with no leaf for a file that is registered and not there). A file that reads again is judged against the text the editor first saw reading, which is what a game started with as far as it can tell: the same text is `applied` (a net-zero edit leaves nothing waiting), any other is `needs_restart`, and the reason says a running game uses it only if it re-reads its data, and otherwise at its next start. A file seen reading for the first time is a baseline, not an edit, so opening a project says nothing; a file first seen refused has no baseline, so what mends it is `needs_restart`. The baseline is kept while a refused registry takes the file out of the verdicts, so an edit made meanwhile is still said when the registry reads again. The registry itself is `applied` when an edit leaves it reading and `refused` with its field (`files[0].path`) when it does not. One edit is one `seq`, and frames without an edit decide nothing. `data_set` over a file that does not scan refuses with the file and the leaf and leaves its bytes as they were.

**A destructible piece's marks and bake name their damage** (#200). `destructible_set` read `destructible.ron`, changed one piece and wrote the whole file back; `destructible_hit` read it and the piece's cached bake. The marks file read with the parser's position and no field, and a bake that did not parse was baked again over the damaged bytes with no word. The two files' schemas (`Marks`, `Bake`, `Chunk`) now live in `bevy_grimoire_core::destructible`, engine-free, so `reload_check::check` reads both kinds in every build: core's own tests hold the three bad files of each (and a damaged chunk, named `chunks[1].points`), while the editor's refusal test needs `--features bevy_carnage`, which the push gate does not build. A file that does not read at all (cut off, a field of the wrong type, a required field missing, a field the type does not have) refuses `destructible_set` (when it marks, which reads the bake) and `destructible_hit` with `destructible.ron (pieces)` or `destructible/site__cart.bake.ron (chunks[1].points)`, says the file is left as it is, and writes nothing, not the marks and not a new bake either; taking a mark off reads no bake and still applies. The bake is a cache, so the way out of a damaged one is to remove the file and the next call bakes afresh. A bake that reads but was made from another mesh or other cut settings is stale, not damaged, and is baked again as before. These two have no watcher: nothing holds either file, so there is no last good value to keep and no one edit to report; the operation that reads the file is the one that refuses.

**A referenced picture says whether it is still a picture** (#200). A reference (`reference_set`) is a project-relative picture an agent is told to look at, and nothing in this repository decodes it, so a file that a full disk cut off, that a text saved over or that was renamed from another format cost the agent a picture it could not open and the author a word nobody said. `bevy_grimoire_core::image_header::read` opens the container's own header (a PNG's `IHDR`, a JPEG's frame header, a GIF's screen descriptor, a WebP's `VP8 `, `VP8L` or `VP8X` chunk; the pixels are never read, and no image crate is a dependency) and answers with the format and the size, or refuses naming the file and the header field: `signature` (empty, or no picture of any of the four formats; the reason says how the file starts, in text or hex), `format` (a picture of one format under another's name), `header` (the first chunk or marker is not the one that carries the size), `width` or `height` (the header ends before the field, or the field is 0), `extension`. `reference_view::sync_reference_view` (registered by `AfterEditPlugin`) looks at the open map's `references.ron` and every picture it lists each frame by size and modification time, and reads a picture that moved (or every one, once a second: a file written in two steps, or twice inside one timestamp tick, looks alike) a few kilobytes at a time, the first megabyte when a JPEG's frame header is not reached. It decides each edit once into `grimoire_state.reloads` as kind `reference_images`: `refused` with the file and the field, said once on the status line, or `applied` when a refused picture is a picture again or an edit left one that reads as other dimensions. A picture first seen reading is a baseline, not news; a listed picture that is not there is not decided here (`grimoire_state.references` says `missing: true`, and a project may name a file it is about to add); a picture that is deleted, or a reference taken back, is forgotten. Nothing is written and `reference_set` still takes any file with an image extension: the editor's own tests drop files that are not pictures. Tests: core `a_reference_image_names_its_field` (the three bad files of every format: corrupt, the wrong type, a header cut off at the width or the height) and the editor's `a_reference_image_that_does_not_read_is_named`.

**A family crate's settings are read as the crate's own type** (#200). The host called a settings file `applied` once it was valid RON and left the crate's own type to refuse it on the status line, so `grimoire_state.reloads` said a file landed that the crate had thrown away (an elements file with a typo'd field, a skin with a number for its accent). In a build that has the crate, `family_host::read_as` reads the file with `reload_check::read` as `ElementsSettings` (`bevy_elements`) or `GooeySkin` (`bevy_gooey`), the crate's own types, so a refusal names `family/<crate>.ron` and the field (`clock`, `climate` for a missing required one, `accent`), is said once, and the text never reaches `FamilySettings`: what a crate applies is always a text its type reads, and the previous settings stay. A file that is not RON at all is refused as before, and names the field where the type stopped reading when the build has the type. A file of the wrong type when the project opens is named from the start and the crate's defaults apply; one deleted is forgotten. A crate this build does not have the type of is held to being RON, which the watch has already seen (a refusal of its own type would need its feature). `bevy_gooey` is in every build since UI-01 (#209: the editor's UI is gooey, and `EditorUiPlugin` is the one plugin that adds it), so its case runs in the default build; the `bevy_elements` case needs `--features bevy_elements`, which the push gate does not build: `family_settings_typed_verdicts`. In that build `family_settings_verdicts`, `family_settings_at_launch` and `family_settings_reload` write `(sun: (hour: …))` as the `bevy_elements` file, which `ElementsSettings` refuses; their fixture text is #152's second half.

With these two, every kind in the registry has a reader that names the file and the field when it does not read: core's `reload_check::check` for 24, the editor's readers for `forest`, `people`, `scripts` and `trees`, and its watchers for `checks`, `oplog`, `game_data`, `reference_images` and `family`. Two of them are not checked in every build: `family` is typed only with the crate's feature, `forest` and `trees` with `bevy_flora`.

## The editor shows each file's reload state (#203)

After an edit the author asks whether the running game took it. `grimoire_state.reload_files` and the Reload panel of the inspector answer it for every file of the open project, one row each: the files `reload::KINDS` names, found on disk, plus any file a verdict names that is gone. Each row says one of `no_game_connected` (no game verdict has reached the editor, so nothing has answered any file), `pending` (the file was written after the game's last decision, so that decision is about earlier text; the row keeps that decision's time beside the file's own), `game_applied` and `game_refused` (the game's decision on the file's current text, with the field and the reason for a refusal and the time it decided), `needs_restart` (the game's decision says so, or the editor says it of a kind it holds, `rigs` and `game_data`, while a game is connected) and `not_read` (a game is connected and its last decision did not read the file: the notes, the plan and the family settings are the editor's own). The editor's own verdict on the file (`grimoire_state.reloads`) rides beside it as `editor`, so a notes file the editor refuses reads `no_game_connected` and `editor: refused` at once.

The panel's header says whether a game is connected (`no game connected (31 files)`, or `game decided 2 s ago (decision 4)`) and lists a line for each file with news: `kits.ron · game applied 2 s ago`, `maps/town.map.ron · game refused (placements[0].at[1]): 1:47: Expected float · 2 s ago`, or `rigs.ron · needs restart: ...`. A file nobody has an answer on is counted in the header and not listed.

**A connected game is one whose verdict the editor has read.** The editor reads `.live/game.ron` only when it runs with `--live` (a test pins that it never reads it otherwise), so without `--live` every row says `no_game_connected`, `grimoire_state.reload_files.game.watching` is `false` and the panel's header says to start the editor with `--live`, rather than claiming no game runs. The game writes nothing at start, so a game that has closed leaves its last verdict standing and the row's time says how stale it is. A heartbeat from the game would say more; it is not built.

**The editor reads the verdict where the game writes it**: the project directory (the one holding `kits.ron`). It used to look only in the authoring kit's directory, which a game never writes to, so a real game's verdict never reached `grimoire_state.game`; it still reads the kit's directory when the project's has none. The tests are `crates/bevy_grimoire_mapper/tests/a_file_says_what_the_game_made_of_its_edit.rs`.

## Runtime state keeps its identity across a reload (#201)

A reload that draws a piece again throws away whatever a game hung on its `Entity` (a booking, an animation phase, a camera target), even when the edit did not touch the piece. So the game-side `GrimoireLivePlugin` keeps an entity for every placement whose definition did not change, and the contract for what counts as a change is one function, `bevy_grimoire_core::live::same_but_id`, that the diff and the plan both use.

|edit|what happens to the entities|
|---|---|
|move, turn, retint or retune a placement, or change its lift, tip, paint, owner, note or family settings|that placement's entity is despawned and drawn again, and so is whatever rests on it (a rider follows its host)|
|change a placement's descriptor (its kind)|the same: that placement and what rests on it|
|edit a descriptor in the library|every placement of that descriptor is drawn again, and what rests on them, and every piece whose resolved height the edit changed|
|change the id of a placement and nothing else|the entity is kept, its `Placement` component holds the new id (a rename)|
|rename a host, and name it in the rows resting on it|the host and its riders keep their entities and the riders stay mounted|
|change a stamp's id (every row it lays is named `<stamp id>/<path>` and a rider's host is renamed with them)|every row keeps its entity: the pairing runs in rounds, hosts first|
|rename a placement and edit it in the same save|the piece is a new piece: the old entity is despawned and a new one drawn|
|write the same content again|nothing is drawn|
|a piece is drawn again (the first rows) and the game registered a migration hook|the hook runs once for that piece, with the old entity alive and the new one drawn, so the state a game registered follows the piece to its new entity|
|an edit leaves a piece alone, or removes it|no hook runs for it|
|a piece is drawn again and a game registered a reference hook (`follow_respawn`)|every component of that kind in the world is rewritten once for the reload, so what named the old entity (a person's home, a list of places) names the new one; one that named a piece the edit removed, or a piece kept, is left as it was|

A rename is found by content: an id only the old map has and an id only the new map has whose rows are equal in every other field (`diff_maps_renaming`, which a reload uses, fills `MapDiff::renamed`, sorted by old id; the plain `diff_maps` takes an id for the piece and never guesses). It is not guessed when it is ambiguous: a pair is made only when the old row has exactly one equal among the new ids and that row has exactly one among the old ids, so two stacked pieces with one row that are both renamed are drawn again. An id both maps have is never a candidate. `same_but_id` lists every field of `Placed` one by one, so a field added to the row stops the build until it is decided. The tests are `crates/bevy_grimoire_core/tests/live_diff_renames.rs` and `crates/bevy_grimoire/tests/live_identity.rs`, which counts the entities a reload draws.

**One hook per kind of state, not one per call site.** A game registers how a kind of state moves once, on the app, with `GrimoireLiveApp` (`bevy_grimoire::live`): `app.carry_across_respawn::<C>()` copies component `C` from the old entity to the new one when the old one has it, and `app.migrate_on_respawn(|world, old, new| …)` is the general form for state that is not a plain copy (it can read the old entity, write the new one, and rebuild what refers to either). The hooks run in registration order, in the same command flush that draws the new entity and before the old one is despawned, so the new entity already has its `Placement`, `OfDescriptor`, `Transform` and `MountedOn`. A rider drawn again with its host is migrated too. A piece that is removed has no new entity, and one renamed and edited in one save is a new piece (its meaning changed), so neither runs a hook. The tests are `crates/bevy_grimoire/tests/live_migrate.rs`.

**What points at a piece follows it too.** A person is not a placement, so a reload never draws them and their position and ties are untouched by any edit to a piece. But a person names the pieces of the map (a society's `Home(entity)`, a list of bound places), and a piece drawn again has a new entity, so a name left alone would point at an entity that is gone. A game says how a kind of reference reads the entity it names, once, on the app: `app.follow_respawn::<Home>(|home, respawned| home.0 = respawned.follow(home.0))`. After a reload that drew at least one piece again, the closure runs for every `Home` in the world, with a `Respawned` that answers `follow(entity)` with the entity that stands for it now and with the same entity for anything a reload did not draw again (a piece it kept, a piece it removed, an entity that is not a placement). A component is marked changed only when `follow` answered with another entity, so a rewrite that changed nothing wakes nothing. It is a closure and not `MapEntities` because a game cannot implement that trait for another crate's component (`bevy_society::Home`). The tests are `crates/bevy_grimoire/tests/live_references.rs`: an edit to an unrelated piece leaves every person, their ties and their homes as they were (a piece in the same map is edited and drawn again, so the hooks run, and no piece a person names gets a new entity and nothing is flagged), and moving a house gives the person living in it the new entity, with the lamp on it followed too, while their position and ties do not change.

What is not done yet (#201 stays open): a society that runs inside the editor. A society's people are not entities of this crate (the game spawns them from `people/<map>.ron` and keeps their position and ties), `people_run` is a one-shot headless run and nothing in this repository holds people across a reload; a rename of a placement a person names (`home` or `work`) is not followed in that file, and there is no alias table for a rename together with an edit or for a renamed map. The first row says a move, a turn, a retint or a retune draws the piece again, which `crates/bevy_grimoire/tests/live_reload.rs::an_edit_respawns_only_what_changed` pins; the issue's split (a move or a turn keeps the entity and updates it in place, and only a change of kind draws it again) needs that assertion changed, which only the owner can grant, and until then a migration hook is how state survives a move.

## The asset system against the watcher (#204)

**Recommendation: keep the editor's own watchers. No migration.** The question (H7) was whether `FileWatch` and the editor's by-name stat poll should be Bevy's `AssetLoader` with its file watcher. A spike loaded `standards.ron` through Bevy's asset system beside them and compared the two on what the issue named: code size, latency from a write to a reload, test determinism, and a replace by rename (H2). The audit below found no open bug that traces to the custom watchers (the one in `watch.rs`, #158, an optional file created while the editor was open that was taken for a first sighting, is fixed: `Watched::absent`), so by the issue's own rule this closes without a migration.

The spike is `bevy_grimoire_mapper`'s cargo feature `asset_spike` (it turns on Bevy's `file_watcher`, the `notify` crates, and nothing else; no build without the feature contains any of it): `src/asset_spike.rs` is the loader (`StandardsLoader`, which reads with `Standards::parse`, the reader the reload verdict names) and a headless app with the watcher on, `tests/asset_spike.rs` has its tests and `examples/asset_spike_measure.rs` the measurements below.

```text
cargo test -p bevy_grimoire_mapper --features asset_spike --test editor asset_spike::
cargo run --release -p bevy_grimoire_mapper --features asset_spike --example asset_spike_measure -- 20 25
```

**Latency from a write to the reload being due**, in ms as median (min to max) over 20 writes each, with the write spread over every phase of each watcher's cycle. Both ways of writing were tried: in place (`std::fs::write`, how the writers wrote before #199) and replaced by rename (`atomic_file`, how every writer writes now). Every write was seen by every watcher (20 of 20 in every row, both platforms).

|watcher|Linux x86_64 (inotify), in place|Linux, by rename|macOS aarch64 (FSEvents), in place|macOS, by rename|

Linux is a debug build on a 24-core host (big), macOS a release build on an M4 Pro (bmb); the write is made and the app stepped every 4 ms (a step took about 4 ms on Linux and 5.6 ms on macOS, which is why the example's `frames` columns differ between them), and an editor's frame adds the same to every column. The editor's stat poll is the rule of `tick_watch` written out for one file, not the editor's own code run.

**What the numbers say, and what they do not.**

- **A rename over the file reaches Bevy's watcher, on both platforms.** That was the open question: Bevy's unprocessed asset server acts on `ModifiedAsset` and `AddedAsset` and ignores a `RenamedAsset` (`bevy_asset-0.20.0/src/server/mod.rs`, `handle_event`), so whether a replace by rename arrived depended on which events the platform's watcher made of it. On Linux and macOS it arrives as a change to the target, in 40 of 40 replaces by rename. `bevys_watcher_reloads_the_asset_after_a_write_in_place_and_after_a_rename_over_it` pins it.
- **Latency is not a reason either way.** Bevy's is fixed by its 300 ms debounce and a 75 ms tick of the debouncer: 0.3 to 0.4 s, between the editor's stat poll (0 to 0.25 s) and the game's default `FileWatch` (0.5 to 1.0 s), slower than the 0.1 s family setting. Nothing here is bound by latency; the target is about a second.
- **A save of several files is not one event.** The editor writes a project as several files, and the asset system tells each one apart. Three files written 25 ms apart reached the asset system spread over a median of 74 ms on Linux (74 to 78) and 81 ms on macOS (0 to 88): 20 of 20 saves on Linux and 14 of 20 on macOS landed in more than one 60 fps frame, because the debouncer delivers in 75 ms ticks and a save straddles one. With the files 2 ms apart, 0 of 20 saves on Linux and 4 of 20 on macOS (0 to 84 ms) did: whether a save straddles a tick is a matter of where it falls, and the gap between the files of a real save is the cost of an atomic write (`atomic_file` flushes the file and then the directory), which lies between those two cases. `FileWatch` said exactly one reload was due after every one of those 80 saves. A consumer of asset events that must read the map, the library and the compositions together would have to rebuild, over asset events, the settle that `FileWatch` is. That is the reason `live.rs` gives for stating the files itself, and the measurement agrees with it.
- **A test of the asset path needs the wall clock.** The same write arrived after 311 to 381 ms on Linux depending on where it fell in the debouncer's tick, an operating-system event handed to a thread and then to a task pool; the spike's three tests take 2.4 s when everything arrives, and each wait is a poll with a timeout (10 s for a first load, 5 s for a change). `FileWatch::poll(now)` takes the clock as an argument, so `crates/bevy_grimoire_core/tests/atomic_writes.rs` feeds it twelve polls and asserts the exact count, in microseconds and with no failure mode of a slow machine.
- **Bevy's watcher can panic on a path the editor accepts.** The first macOS run of the example, in `std::env::temp_dir()`, which is `/var/folders/...`, lost all 60 writes of the three-file scenario to `thread 'notify-rs debouncer loop' panicked at bevy_asset-0.20.0/src/io/file/file_watcher.rs:64: FileWatcher::get_asset_path() failed to strip prefix from absolute path: absolute_path=/private/var/folders/.../.c.ron.80679-138.tmp, root=/var/folders/...`: FSEvents reports the canonical path (`/private/var`) and Bevy compares it with the root as it was given. The example and the tests now canonicalize the root. A project under a symlinked directory (`/tmp`, a linked drive) would be the same case for the editor, which stats the path it was given and has no such step.
- **Code size is not a saving.** `FileWatch`, its directory walk and its settle rule are 94 lines of code in `bevy_grimoire_core::live`; the editor's by-name poll and adoption in `watch.rs` are 244. The spike is 72 lines for one kind, and it replaces only the question "did this file change": the project set the editor watches by name, the check that an editor's own save is not a change (`differs`), the verdict (`reload_check`, `grimoire_state.reloads`, the reload panel) and the last-good-state rule all sit above the watcher and are needed with either. A refused file keeps the last good asset in Bevy too (`a_refused_reload_keeps_the_last_good_asset`), which is the one thing a migration would have given for free, and every watcher here already does it.

**When to read this again.** Move to the asset system if a kind has to load off the main thread anyway (a large mesh or a texture), or if Bevy's watcher gains a settle across a set of files (one event after the writes stop, as `FileWatch` has). Neither is true of the editor's `.ron` files, which are small, read whole and read together. Until then the spike stays behind its feature, with its tests, as the measurement to repeat.

## What the audit found

These are the facts the later issues in the series start from.

- **The game's watcher sees every `.ron` under its directory** (`GrimoireLivePlugin`, the extension set `{ron}`) and runs the whole project load. It diffs placements, the library and masks. A change to a kind it does not read (notes, plans, references, forests) fires a reload that changes nothing, and a broken file of such a kind does not turn the verdict false, because nothing parses it. The class column names what each kind costs, not what the watcher notices.
- **The editor watches by name** (`watch.rs`): `kits.ron`, `vocab.ron`, `compositions.ron`, `rules.ron`, `standards.ron`, `repetition.ron`, each kit's `library.ron` and `project.ron`, and the open map. Terrain, water, volume, forest and tree files are polled by modification time in the views that draw them, and family settings by the family host every 0.1 s. Notes are looked at every frame by size and modification time.
- **A file that does not read keeps the last good state in the project watcher, the game, the terrain view, the forest view, the tree files the forest draws from, the notes view and the family settings** (the editor says "kept what it had"). The editor's views and watchers report each edit in `grimoire_state.reloads`, and since #200 slice 12 every kind in the registry has a reader that names the file and the field.
- **Every write of a project file is atomic since #199.** The audit found `family`, `game_data`, `people`, `forest`, `scripts`, `terrain`, `trees`, `volume`, `water_plan`, `water_field`, `destructible_marks`, `destructible_bake`, `reference_images`, and `kits` and `vocab` at project creation written in place, so a reader could see half a file. All of them now go through `bevy_grimoire_core::atomic_file`: a uniquely named hidden temp file (`.<name>.<pid>-<n>.tmp`, never a `.ron` and skipped by the watcher) beside the target, flushed, renamed over it, then the directory flushed. A reader thread parses a map while it is replaced ten thousand times without the flushes and three hundred times with them, a writer process is killed at forty random points, four threads write one path, and `tests/atomic_writes_only.rs` fails on a new plain `fs::write`, `File::create`, `fs::copy` or `OpenOptions` in the non-test source of `bevy_grimoire_core` and `bevy_grimoire_mapper` (a write through another API is not seen by it). What is promised is no torn read and no half-written file after the writer dies; durability against power loss is not, because a test cannot show it. Caches (thumbnails, the animation bench cache) use `write_cache`, the same rename without the flushes.
- **`game_data` is a `Restart` kind** because `data_set` writes files the game owns and this repository ships no reader for them. Whether a game re-reads them is the game's. #202 moves behaviour into data and scripts so the list shrinks.

## What is not a kind

These are written but are not project data, so they have no class. None is read back as project data.

- `<grimoire>/.live/game.ron`, the game's verdict on its latest reload. The game writes it, and the watcher skips every name that starts with a dot so it cannot trigger the reload it reports.
- `slop/llm/vocab_proposals.ron`, a VLM's label proposals, `target/grimoire_thumbs/`, `target/anim_bench_cache.ron` and `target/loop/captures/snips/`: caches and captures.
